# next — 다음 할 일 고르기

목표와 현재의 차이(갭)에서 이슈 후보를 뽑아 보인다. **범위를 넓히는 결정은 사람이 한다.** AI는 후보를 제안하고, 사람이 확인한 것만 이슈로 등록한다.

## 읽는 것

| 구분 | 읽는 곳 | 이유 |
|---|---|---|
| 목표 | `docs/product/PRD.md`, `docs/product/로드맵.md` | 무엇을 만들기로 했는가 |
| 정본 | 기능 페이지(`docs/features/`), 도메인 모델 | 규칙이 어떻게 정해졌는가 |
| 사실 | `src/`, `docs/generated/` | 실제로 무엇이 있는가 |
| 진행 | 열린 이슈(`gh issue list`), 이전 sketch의 "한계와 후속" | 이미 있는 일, 미뤄 둔 일 |
| 교훈 | `docs/records/pitfalls.md` | 같은 실수를 이슈로 막을 수 있는가 |

읽을 파일이 많아서 **갭 탐색은 내장 Explore 에이전트에 맡긴다**(새 에이전트를 만들지 않는다). 프롬프트에는 찾을 것과 읽을 경로만 주고, 결론과 근거 위치(파일·ID)만 돌려받는다. 이유: 파일 내용이 메인 컨텍스트를 채우지 않게 한다.

## 절차

1. **현재를 파악한다.** 열린 이슈와 로드맵 체크박스를 먼저 읽는다. 이미 이슈가 있는 일을 새로 제안하지 않기 위해서다.
2. **갭을 찾는다.** 목표에는 있는데 현재에 없는 것을 찾는다. 로드맵·정본에 없는 갭도 후보에 올린다(예: 규칙은 있는데 테스트가 없음, 이전 sketch가 후속으로 미룬 일, `pitfalls.md`가 막아 주지 못한 반복 실수).
3. **후보 3~5개를 보인다.** 많이 찾는 것보다 중요한 것을 고른다. 후보마다 아래를 적는다.

| 항목 | 내용 |
|---|---|
| 후보 | 한 줄 요약 |
| 이유 | 어떤 갭인가, 근거 위치(파일·ID·이슈) |
| 이슈 상태 | **새 이슈 필요** / **기존 이슈 있음(#번호)** / **이슈 본문이 낡음(#번호, 어디가 낡았나)** |
| 크기 | 작은 일 / 일반 이슈 (`SKILL.md`의 크기 구분 질문) |

4. **범위를 확인한다.** 후보가 PRD 범위 밖이면 이슈로 올리기 전에 "범위에 넣을지"를 사람에게 묻는다. AI가 범위를 넓히지 않는다. 이유: 범위가 합의 없이 커지는 것을 막는다.
5. **사람이 고른다.** 사용자가 고른 후보와 수정 사항을 받는다. 고르지 않은 후보는 만들지 않는다.
6. **등록한다.** 사람이 확인한 초안만 만든다.
   1. 요청서 양식(`.github/ISSUE_TEMPLATE/요청서.md`)으로 초안을 보이고 확인받는다.
   2. `gh issue create`로 등록하고(`ask`라 도구 권한 확인도 뜬다) assignee를 붙인다.
   3. 로드맵에 항목이 필요하면 이슈 번호가 정해진 뒤에 올린다. 번호는 등록해야 알 수 있어서 이 순서다. 로드맵 수정은 그 이슈를 처리하는 PR에서 같이 한다(`개발-워크플로.md`의 로드맵 규칙).
   - 기존 이슈의 본문이 낡았으면 새로 만들지 않고 고칠 내용을 보여 확인받은 뒤 `gh issue edit`한다.
7. **넘긴다.** 사용자가 바로 시작하자고 하면 `start`로 간다. 아니면 후보 목록만 남기고 끝낸다.

## 하지 않는 일

- 사람이 확인하지 않은 이슈를 만들지 않는다.
- PRD 범위를 AI가 넓히지 않는다.
- 이미 이슈가 있는 일을 새 이슈로 중복해 만들지 않는다.
- 후보를 보이면서 구현을 시작하지 않는다.
