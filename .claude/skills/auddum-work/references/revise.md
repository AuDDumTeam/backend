# revise — PR 코멘트 처리

PR에 리뷰 코멘트가 달린 뒤의 길이다. 처음부터 다시 하지 않고, 코멘트가 무엇을 바꾸느냐에 따라 돌아갈 지점을 정한다.

## 시작

1. **PR을 정한다.** 입력은 PR 번호다. 없으면 현재 브랜치의 PR(`gh pr list --head <브랜치>`)을 쓴다. 없으면 `pr`로 보낸다.
2. **코멘트를 읽는다.** `gh pr view <n> --comments`와 인라인 리뷰 코멘트(`gh api repos/{owner}/{repo}/pulls/<n>/comments`). 이미 해결됐거나 답이 달린 것은 제외하고 **열린 코멘트**만 모은다.
3. **하나씩 분류한다.** 코멘트마다 아래 네 분류 중 하나를 붙여 사용자에게 한 번에 보인다(코멘트 | 분류 | 이유). 처리는 그 뒤에 한다.

## 분류

| 분류 | 기준 | 돌아가는 곳 |
|---|---|---|
| ① 코드만 | 동작과 규칙은 그대로이고 구현·테스트·이름·포맷을 고친다 | 코드 수정 → build |
| ② 정본 문장만 | 정본(기능 페이지, 도메인 모델 등)의 표현·연결이 틀렸고 코드는 맞다 | 정본 수정 → fact-verifier |
| ③ 규칙·의도 변경 | 정책, 도메인 규칙, 응답, API가 바뀐다 | sketch부터 다시(`start`) |
| ④ 질문·반박 | 코드 수정이 필요 없다. 이유를 묻거나 다른 의견이다 | 답글 |

**분류가 애매하면 AI가 정하지 않고 사람에게 묻는다.** 이유: ③을 ①로 잘못 분류하면 합의 없이 규칙이 바뀐다. 한 코멘트가 둘 이상에 걸리면 나눠서 각각 분류한다.

## 분류별 처리

### ① 코드만

1. 고치고 `./gradlew build`를 돌린다. 실패하면 2회까지 고치고 그래도 실패하면 중단해 보고한다.
2. 동작이나 테스트의 검증 내용이 바뀌었으면 코드 리뷰를 다시 한다(재리뷰 기준과 호출은 `build.md`). 이름·주석·포맷·문서만이면 생략한다.
3. 커밋한다(확인 후). 메시지는 `docs/howto/개발-워크플로.md`의 규칙을 따른다.

### ② 정본 문장만

1. 정본 문장을 고친다. 코드는 건드리지 않는다.
2. fact-verifier만 부른다. 입력과 판정 처리는 `wrap.md`를 따른다. 코드 리뷰는 다시 하지 않는다.
3. 커밋한다(확인 후). 정본 변경 커밋이다.

### ③ 규칙·의도 변경

1. 코드나 정본을 고치지 않고 멈춘다. 코멘트가 sketch의 어느 규칙을 바꾸는지 정리해 사용자에게 알린다.
2. sketch를 고치고 `status`를 `초안`으로 되돌린다. `start`의 sketch-reviewer와 승인 절차를 다시 거친다. **승인 없이는 구현하지 않는다.** 항상 사람이 승인한다.
3. 승인되면 `build`부터 다시 하고, 이어서 `wrap`, 그다음 이 라우트로 돌아와 나머지 코멘트를 처리한다.

### ④ 질문·반박

1. 코드를 고치지 않는다. sketch와 정본을 근거로 답글 초안을 쓴다. 근거가 없으면 지어내지 않고 사용자에게 묻는다.
2. 반박이 맞다고 판단되면 ③으로 다시 분류한다.

## 답글

- 초안을 사용자에게 보이고 확인받은 뒤 게시한다. 외부에 보이는 행동이므로 `gh pr comment`는 도구 권한 확인도 한 번 더 뜬다(`ask`).
- 단순한 "수정했습니다 (커밋 해시)" 답글은 초안 확인을 생략하고 올린다. 도구 권한 확인은 그대로 뜬다. 이유: 사실을 알리는 한 줄이라 내용을 확인받을 것이 없다.
- 답글에 근거(sketch 줄, 정본 파일·ID, 커밋)를 적는다.

## 기록

- **sketch 결과 칸.** 리뷰에서 코드나 정본이 달라진 점을 "리뷰에서 달라진 점"으로 적는다. 이 칸은 PR 본문의 한계·후속에도 반영한다.
- **교훈.** 같은 종류의 지적이 반복되면 `docs/records/pitfalls.md`에 추가한다(한 번 겪으면 교훈, 두 번 겪으면 규칙으로 올린다). 비슷한 항목이 있으면 관련에 이슈를 더한다.

## 재진입 판정

처리를 마칠 때마다 판단한다.

| 상태 | 다음 |
|---|---|
| 열린 코멘트가 없고, 필요한 검사(build, 해당 리뷰, fact-verifier)가 통과 | 머지 대기. PR이 Draft면 Ready로 바꿔 달라고 알리고 머지는 사람이 한다 |
| 열린 코멘트가 남았거나 검사가 실패 | 다시 이 라우트 |

세션이 끊겨도 같은 판정을 한다. PR의 열린 코멘트, sketch `status`, `_workspace/`의 최신 리포트로 어디까지 했는지 알 수 있다.

## 하지 않는 일

- 분류가 애매한 코멘트를 임의로 처리하지 않는다.
- ③을 승인 없이 구현하지 않는다.
- 코멘트가 없는 변경을 끼워 넣지 않는다.
- `gh pr merge`를 쓰지 않는다.
