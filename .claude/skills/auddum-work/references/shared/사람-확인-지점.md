# 사람 확인 지점

사람이 정하거나 승인해야 넘어가는 지점의 정본이다. 라우트 파일은 여기를 가리키기만 한다.

| 지점 | 누가 | 이유 |
|---|---|---|
| 목표와 범위(PRD·로드맵), 범위를 넓히는 결정 | 사람 | AI가 범위를 넓히면 합의 없이 일이 커진다 |
| 이슈 선택·등록(`gh issue create`는 `ask`) | 사람 | 외부에 보이고 되돌리기 어렵다 |
| sketch 승인("승인합니다"·"진행해"·"ㄱㄱ") | 사람 | 승인 전 구현 금지. `status`를 `승인됨`으로 바꾸는 근거다 |
| 커밋 | 사람 확인 후 | 메시지와 변경 파일을 보이고 확인받는다 |
| push, PR 생성(`gh pr create`는 `ask`), PR 코멘트(`gh pr comment`는 `ask`) | 사람 확인 후 | 외부에 보인다 |
| FAIL 판정(규칙 충돌, 코드·sketch 불일치), 재시도 2회 후 미해결 | 사람 | 기준을 AI가 낮춰 통과시키지 않는다 |
| PR 머지, `develop → main`, 배포 | 사람만 | `gh pr merge`는 deny, 브랜치 보호가 막는다 |

`develop`·`main` 직접 push와 force push는 누구도 하지 않는다.

## 스테이징과 비밀 값

- 경로를 명시해 스테이징한다. `git add -A`·`git add .`는 쓰지 않는다. 이유: 의도하지 않은 파일(비밀 값, 산출물)이 섞이는 것을 막는다.
- `.env`와 `.env.*`(`.env.example`은 샘플이라 예외)는 절대 스테이징하지 않는다. `application-local.yaml`은 비밀 값 없이 환경 변수 참조만 두므로 커밋 대상이지만, 스테이징 전에 실제 값이 들어갔는지 확인한다.
- 커밋 전에 `git status`로 위 파일이 없는지 본다.

## 권한 설계 이유

`.claude/settings.json`의 권한은 세 종류로 나눈다.

- `allow`: 읽기·조회성 명령과 컴파일·테스트 명령만 둔다. `git add`·`git commit`·`git switch`·`git push`는 넣지 않아서, 사람이 확인한 뒤에도 실행마다 권한 확인이 한 번 더 뜬다.
- `ask`: `gh issue create`, `gh pr create`, `gh pr comment`. 외부에 보이는 행동이라 매번 확인한다.
- `deny`: `.env`·`.env.*` 읽기, `rm -rf`, `main`·`develop` push, force push, `gh pr merge`. 되돌리기 어렵거나 사람만 해야 하는 행동이다.

이유: 외부에 보이거나 되돌리기 어려운 행동은 사람 확인 뒤에도 한 번 더 막는다.
