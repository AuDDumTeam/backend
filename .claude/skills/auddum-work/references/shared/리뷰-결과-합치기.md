# 리뷰 결과 합치기

domain-reviewer와 code-reviewer를 병렬로 부르면 리포트가 둘이다. 리뷰어는 서로의 리포트를 보지 않는다(보면 한쪽이 다른 쪽을 따라가서 독립 검증이 사라진다). 합치는 일은 오케스트레이터가 한다.

- **원문은 그대로 저장한다.** 합치기 전에 각 리포트 전문을 `_workspace/`에 저장하고 사용자에게 보인다.
- **리뷰어의 사실 주장은 반영하기 전에 직접 확인한다.** 리뷰어는 읽기 전용이라 틀린 사실을 근거로 삼을 수 있다(예: "이 파일만 이 어노테이션을 쓴다"가 실제로는 17개 파일). 틀린 근거면 지적의 결론이 맞는지 따로 판단한다.
- **겹치는 지적은 하나로 합친다.** 같은 위치·같은 원인이면 한 항목으로 쓰고 두 리뷰어가 모두 지적했다고 적는다. 어느 쪽 ID로 올릴지는 더 무거운 쪽을 따른다.
- **판정은 더 나쁜 쪽이다.** FAIL > PASS_WITH_FIXES > PASS.
- **둘이 충돌하면 고르지 않는다.** 한쪽은 문제라 하고 다른 쪽은 문제없다고 하면 사람에게 올린다.
- **FAIL은 사람에게 올린다.** 책임을 나눠 보인다: 코드는 구현(메인 스레드), 정본 문장은 wrap, 규칙·의도가 바뀌면 sketch부터 다시.
- **설계 제안(선택)은 판정과 무관하게 보인다.** 채택하면 후속 이슈나 `설계-결정.md`로 남긴다.
- **확정된 결정과 충돌하는 지적은 오탐으로 본다.** `설계-결정.md`에 빠진 결정이 없는지 확인한다.
- **재리뷰는 동작이나 검증이 바뀐 경우만 한다.** 이름·주석·포맷·문서만 바뀌었으면 생략하고 PR 본문에 "리뷰 후 가독성 수정"으로 적는다. 애매하면 재리뷰한다.
