# build — 테스트 먼저, 구현, 검증, 리뷰

승인된 sketch를 테스트와 구현으로 바꾸고, 도구와 두 리뷰어로 검증한다. 검증은 도구가 먼저, 판정은 서브에이전트가 한다. 구현은 메인 스레드가 한다.

## 시작 조건

- sketch `status`가 `승인됨`이다. 아니면 구현하지 않고 `start`로 돌려보낸다. 이유: 승인 전의 구현은 버려지기 쉽다.
- 브랜치가 `feature/<n>-…`이다. `main`·`develop`이면 멈춘다.

## 이어받기

시작할 때 `_workspace/<run-id>/`를 읽어 어디까지 했는지 정한다. 파일 이름은 `shared/작업-산출물.md`를 따른다.

| 있는 것 | 이어받는 단계 |
|---|---|
| 없음 | 1(테스트 먼저) |
| test-writer note, 구현·build 전 | 2(구현) |
| 커밋이 있고 diff·리포트가 없음 | 4(리뷰) |
| 리뷰 리포트가 있음 | 5(합치기)나 6(FAIL 처리). 가장 큰 r<k>를 기준으로 한다 |

읽은 결과를 한 줄로 알리고 해당 단계에서 시작한다. 애매하면 사용자에게 묻는다.

## 절차

1. **테스트 먼저.** test-writer를 부른다. 입력은 sketch 경로와 `sources`의 정본 절 경로뿐이다(내용을 붙여 넣지 않는다). 끝나면 note를 확인하고 직접 `./gradlew compileTestJava test`를 돌려 **red**를 확인한다. 이미 통과하는 테스트가 있으면 이유를 사용자에게 보고한다. note의 `## 사용자 질문`·`## Objections`는 그대로 전달한다.
   - 리팩터링은 기존 테스트가 안전망이다. sketch의 규칙 표에 테스트가 없는 규칙이 있을 때만 먼저 test-writer로 보강한다.
2. **구현.** sketch의 구조·순서와 테스트 칸을 따라 `src/main/**`을 쓴다. 지킬 규칙 칸의 문서(컨벤션, 아키텍처)를 따른다. 구현 중 sketch와 다르게 해야 하면 아래 "sketch와 달라질 때"를 따른다.
3. **green과 build.** `./gradlew test`로 green을 확인한 뒤 `./gradlew build`를 돌린다. 실패하면 리뷰 전에 고치고, 같은 실패는 2회까지 고친다. 그래도 실패하면 중단하고 보고한다. 이유: 도구가 최종 판정이라 에이전트의 PASS가 build를 대신하지 않는다.
   - test-writer가 BUG로 보고한 항목은 구현을 고친다. 정본과 sketch를 보고 테스트가 틀렸다고 판단되면 고르지 않고 사용자에게 묻는다.
4. **커밋.** green 직후에 한 번 커밋한다(커밋 → 리뷰 → 반영 커밋). 이유: 리뷰한 대상이 커밋으로 고정되어 "리뷰 뒤에 더 바뀌었는가"를 HEAD로 판단할 수 있고, 세션이 끊겨도 이어받기 쉽다. 이 레포는 squash 머지라 리뷰 지적을 반영한 추가 커밋이 쌓여도 최종 기록에 영향이 없다. 테스트와 구현을 나누지 않고 한 커밋에 담는다. 변경 파일과 메시지를 보이고 확인받는다(`shared/사람-확인-지점.md`). 정본은 이 단계에서 고치지 않는다(`wrap`).
5. **리뷰.** diff를 `_workspace/<run-id>/00_diff-r<k>.patch`에 저장한다. domain-reviewer와 code-reviewer를 **같은 메시지에서 동시에** 호출한다. 입력은 diff·sketch 경로뿐이고 서로의 리포트는 주지 않는다. 각 리포트 전문을 `30_domain-reviewer_report_r<k>.md`, `30_code-reviewer_report_r<k>.md`에 저장하고 사용자에게 보인다.
6. **합치기.** `shared/리뷰-결과-합치기.md`를 따른다. 겹치는 지적을 병합하고 더 나쁜 판정을 따른다.

| 합친 판정 | 행동 |
|---|---|
| `PASS` | `wrap`으로 간다 |
| `PASS_WITH_FIXES` | 권고를 보이고 반영 여부를 묻는다. 반영하면 고치고 별도 커밋으로 올리며, 재리뷰 기준에 따라 새 r<k> |
| `FAIL` | 사람에게 올린다. 책임별로 나눈다: 코드는 구현(2단계부터), 테스트는 test-writer 수정 모드, 규칙·의도가 바뀌면 sketch부터 다시 |

7. **재시도.** FAIL은 해당 단계부터 다시 하되 최대 2회다. 넘으면 멈추고 미해결 항목을 보고한다. 기준을 낮춰 통과시키지 않는다.

## 재리뷰 기준

리뷰 뒤 `src/main`의 동작이나 테스트의 검증 내용이 바뀌면 새 r<k>로 다시 리뷰한다. 이름·주석·포맷·문서만 바뀌었으면 생략하고 PR 본문에 "리뷰 후 가독성 수정"으로 적는다. 애매하면 재리뷰한다. 이유: 동작이 바뀐 변경을 리뷰 없이 통과시키는 비용이 더 크다.

## sketch와 달라질 때

| 상황 | 행동 |
|---|---|
| 규칙·정책·API가 바뀐다 | 멈춘다. sketch를 고쳐 `status`를 `초안`으로 되돌리고 `start`의 승인 절차로 다시 간다 |
| 작은 차이(이름, 파일 위치, 순서) | 계속한다. 결과 칸의 "계획과 달라진 점"에 기록해 둔다 |
| 구현 중 새 결정이 필요해진 경우(설정 구조, 테스트 환경 등 규칙은 그대로) | 사용자에게 묻고, 답을 sketch의 질문과 답에 출처와 함께 더한다. 규칙과 접근의 방향이 그대로면 `승인됨`을 유지한다 |
| 판단이 안 서는 차이 | 규칙이 바뀐다고 보고 멈춘다 |

이유: 규칙을 합의 없이 바꾸는 것을 막되, 사소한 차이로 흐름을 끊지 않는다.

## 내장 코드 리뷰

내장 `/code-review`는 필수가 아니다. 큰 변경에서 사용자가 별도로 받고 싶을 때만 안내한다. `/code-review ultra`는 사용자가 직접 실행하는 클라우드 리뷰이고 AI가 시작할 수 없다.

## 하지 않는 일

- 승인 전에 구현하지 않는다.
- 정본을 고치지 않는다(`wrap`).
- 리뷰어가 파일을 쓰게 하지 않는다. 리포트 저장은 메인이 한다.
- 리뷰어끼리 리포트를 보여 주지 않는다.
