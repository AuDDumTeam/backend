# small — 작은 일

동작이나 규칙이 바뀌지 않는 일(오타, 설정, 문서 정리, 정본이 틀리고 코드가 맞는 경우)이다. 의식을 줄이려고 sketch와 리뷰어 없이 가볍게 간다. 이슈가 없어도 된다.

## 절차

1. **요청을 한 줄로 정리한다.** 무엇을 왜 바꾸는지. 이슈 번호가 있으면 `gh issue view`로 읽는다.
2. **크기를 다시 확인한다.** "동작이나 규칙이 바뀌는가?" 하나라도 바뀌면 멈추고 `start`로 올린다(아래 "올리는 경우").
3. **브랜치를 만든다.** `develop`을 최신으로 받고 `chore/<영문-요약>`을 만든다. 이슈가 있는 작은 일도 이름은 `chore/`다. 이유: 작은 일은 sketch가 없어 `feature/`와 구분되어야 재진입 판정이 맞다.
4. **고친다.** 필요한 파일만 읽는다. 문서나 설정이 바뀌면 같은 브랜치에서 어긋난 서술도 함께 고친다.
5. **`./gradlew build`를 돌린다.** 실패하면 2회까지 고치고, 그래도 실패하면 중단해 보고한다. 이유: 작은 일의 유일한 관문이 build라서 건너뛰지 않는다.
6. **커밋한다.** 변경 파일과 메시지(`type(scope): 제목`, 이슈가 있으면 `(#n)`)를 보이고 확인받은 뒤 경로를 지정해 `git add` → `git commit`한다. `git status`로 `.env`가 없는지 본다.
7. **`pr` 라우트로 넘어간다.** 작은 일은 PR 본문에 "문서 영향 없음"과 그 이유를 적고, 확인 절차는 `pr`과 같다. sketch가 없으므로 `status` 칸은 해당 없음으로 쓴다.

## 올리는 경우

하다가 아래가 보이면 파일을 더 고치지 않고 멈춘다. 지금까지의 변경은 커밋하지 않고, 이유와 함께 `start`로 올리자고 사용자에게 알린다.

- 사용자에게 보이는 동작이나 응답이 바뀐다.
- 정책, 도메인 규칙, 상태 전이, API가 바뀐다.
- 정본(기능 페이지, 도메인 모델)을 고쳐야 한다.

이유: 작은 일에서 규칙이 바뀌면 합의(sketch)와 두 리뷰어 없이 규칙을 바꾸게 된다.

## 하지 않는 일

- sketch를 만들지 않는다. 리뷰어를 부르지 않는다.
- `develop`·`main`에 직접 커밋하지 않는다.
