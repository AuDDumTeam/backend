# wrap — 정본 갱신, 교훈, sketch 마무리

`build`가 끝난(리뷰 FAIL 아님, build 통과) 구현의 확정된 규칙을 정본에 옮기고, 독립된 에이전트가 검증한 뒤 sketch를 닫는다. 정본은 확정된 것만 담아야 믿을 수 있어서, 구현 중에는 고치지 않고 여기서 한 번에 고친다.

## 시작 조건

- 브랜치가 `feature/<n>-…`이고 sketch `status`가 `승인됨`이다.
- 마지막 `build`의 두 리뷰어 판정이 FAIL이 아니고 `./gradlew build`가 통과했다. 아니면 `build`로 돌려보낸다.

## 절차

1. **정본에 옮긴다.** sketch의 확정 규칙(요구사항 칸의 규칙 표)을 정본에 쓴다. 기존 규칙을 고치는 것도 포함한다. 어느 문서로 가는지는 `shared/정본-갱신-매핑.md`를 본다. 구현이 sketch와 달라진 곳은 코드가 사실이므로 달라진 쪽을 정본에 쓰고 결과 칸에 기록한다.
   - 옮기면서 이 작업과 어긋난 낡은 서술도 함께 찾는다: "추가 예정"·"도입 여부를 정한다" 같은 이미 지난 표현, 바뀐 설정·경로·포트·명령, 새로 생긴 파일 위치.
   - 하네스 문서(`CLAUDE.md`, `.claude/**`)도 대상이다.
   - 안 고쳐도 된다고 판단하면 PR 본문 문서 영향에 이유를 한 줄 적는다.
   - 이유: 정본이 코드와 어긋난 채 남으면 다음 작업의 기준이 틀어진다.
2. **생성 문서를 다시 만든다.** 코드가 바뀌어 오류 코드·API가 달라졌으면 `docs/generated/README.md`의 "다시 만들기" 명령을 쓴다. 생성 문서는 손으로 고치지 않는다.
3. **이력 표를 맞춘다.** 기능 페이지 하단 이력 표(날짜·변경·sketch·결정·PR)와 sketch 머리말(`features`·`ids`·`decisions`)을 서로 맞춘다. 문서만 고쳤으면 `features: [없음]`이다. 자동으로 확인하지 않으므로 직접 본다.
4. **로드맵.** `docs/product/로드맵.md`의 해당 체크박스(`[x]`)와 이슈 번호를 고친다. 범위가 바뀌었으면 PRD를 고치자고 사용자에게 제안한다(범위를 넓히는 결정은 사람이 한다).
5. **정본 변경을 별도 커밋으로 한다.** 구현 커밋과 분리한다. 이유: 리뷰에서 정본 변경을 따로 볼 수 있다. 변경 파일과 메시지를 보이고 확인받는다. 메시지 규칙은 `docs/howto/개발-워크플로.md`의 커밋 메시지 절이다.
6. **fact-verifier를 부른다.** 정본 변경분을 `_workspace/<run-id>/00_canon-diff.patch`에 저장한다(`git diff <구현 커밋>..HEAD`의 `docs/` 부분). 입력은 patch, sketch, 코드 경로뿐이다. 리포트 전문을 `30_fact-verifier_report_r<k>.md`에 저장하고 사용자에게 보인다. 정본 변경분만 검증하고 코드 리뷰는 다시 하지 않는다.
7. **교훈.** 이번 작업에서 겪은 것 중 **다음 작업에서 같은 실수를 막을 수 있는 것**만 `docs/records/pitfalls.md`에 쓴다(양식은 그 파일 머리). 일어난 일의 기록은 쓰지 않는다. 이미 비슷한 항목이 있으면 새로 쓰지 않고 관련에 이슈를 더한다.
8. **sketch를 닫는다.** 결과 칸을 채우고(무엇을 했는지, 계획과 달라진 점, 한계와 후속) `status: 완료`로 바꾼다. 이 칸이 PR 본문의 초안이 된다. 교훈과 sketch 변경도 커밋한다(확인 후).

## fact-verifier 판정

| 판정 | 행동 |
|---|---|
| `PASS` | 7로 간다 |
| `PASS_WITH_FIXES` | 지적을 보이고 정본 문장·연결을 고친다. 정본이 바뀐 것이므로 새 r<k>로 다시 부른다 |
| `FAIL` | 지적이 정본 문장 문제면 **정본 문장만** 고치고 새 r<k>. 코드와 sketch가 다르다는 지적이면 **멈추고 사람에게** 알린다(어느 쪽이 맞는지는 AI가 정하지 않는다) |

재시도는 2회다. 넘으면 멈추고 미해결 항목을 보고한다. 이유: 기준을 낮춰 통과시키지 않는다.

## 리팩터링

동작과 규칙이 바뀌지 않았으므로 정본을 고치지 않는다. 1~6을 건너뛰고 PR에 "문서 영향 없음"과 그 이유를 적는다. sketch 결과 칸과 `status: 완료`, 교훈(7)은 그대로 한다.

## 하지 않는 일

- 구현 중에 정본을 고치지 않는다.
- 확정되지 않은 규칙을 정본에 쓰지 않는다.
- 생성 문서를 손으로 고치지 않는다.
- fact-verifier 뒤에 코드 리뷰를 다시 하지 않는다. 코드가 바뀌었으면 `build`로 돌려보낸다.
