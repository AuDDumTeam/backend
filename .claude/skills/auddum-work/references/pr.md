# pr — Draft PR

완료된 작업의 PR 본문을 sketch에서 만들어 Draft로 올린다. 머지는 사람이 한다.

## 입력과 전제

| 구분 | 이슈(sketch 있음) | 작은 일(sketch 없음) |
|---|---|---|
| 입력 | sketch `status: 완료` | 변경 내용(`git diff develop...HEAD`) |
| 전제 | 리뷰 통과, 정본 갱신, 로컬 `./gradlew build` 통과 | 로컬 `./gradlew build` 통과 |
| 브랜치 | `feature/<n>-…` | `chore/…` |

전제를 못 채우면 올리지 않고 해당 라우트(`build`, `wrap`, `small`)로 돌려보낸다. 브랜치가 `main`·`develop`이면 멈춘다.

## 절차

1. **최신 상태 확인.** 마지막 리뷰 이후 `src/main`의 동작이나 테스트 검증이 바뀌었으면 재리뷰가 필요하다고 알리고 `build`로 보낸다(재리뷰 기준은 `build.md`). 이름·주석·포맷·문서만 바뀌었으면 PR 본문에 "리뷰 후 가독성 수정"으로 적는다.
2. **본문 초안을 쓴다.** `.github/pull_request_template.md`의 칸을 따른다. sketch의 결과 칸이 초안이다.

| 칸 | 어디서 가져오나 |
|---|---|
| 관련 이슈·sketch | 이슈 번호와 sketch 경로. 작은 일은 "없음" |
| 배경 | sketch 요구사항 칸의 왜 |
| 변경 내용 | sketch 결과 칸 |
| 검토한 대안 | sketch 접근 칸의 검토한 대안 |
| 문서 영향 | 바뀐 정본 목록. 리팩터링과 작은 일은 "문서 영향 없음"과 이유 |
| 리뷰 결과 | 합친 리뷰 판정과 반영한 지적. 리포트 경로는 `_workspace/`라 레포에 없으므로 요약을 쓴다 |
| 테스트 방법 | 실행한 명령과 결과 |
| 한계·후속 | sketch 결과 칸 |
| 체크리스트 | 템플릿 항목을 실제로 확인하고 체크 |

해당 없는 칸은 지우지 않고 "없음"이라고 쓴다.

3. **이슈 연결.** 관련 이슈는 `Closes #n`이다. 큰 이슈를 나눈 PR이면 마지막 PR만 `Closes`, 나머지는 `Refs`다. 완료 기준에 아직 못 한 시험이 있으면 `Refs`로 올리고 본문 한계·후속에 적는다.
4. **제목.** 커밋 메시지와 같은 형식이고 squash 커밋 메시지가 된다. 달라지는 것을 쓰고, 도메인이 아닌 변경은 scope를 생략한다(`docs/howto/개발-워크플로.md`).
5. **확인.** push할 브랜치, 제목, 본문 요약, `Closes`/`Refs` 여부를 보이고 확인받는다(`shared/사람-확인-지점.md`). `git status`로 `.env`가 없는지 본다.
6. **올린다.** `git push -u origin <브랜치>` → `gh pr create --draft --base develop`. 본문은 파일로 만들어 `--body-file`로 넘긴다. 실패하면 우회하지 않고 보고한다.
7. **알린다.** PR 주소와 "빌드 체크가 통과하고 sketch가 `완료`이면 Ready로 바꾼 뒤 머지해 달라"고 알린다. 머지는 하지 않는다.

## 하지 않는 일

- `gh pr merge`를 쓰지 않는다. `develop`·`main`에 직접 push하지 않는다.
- 본문을 sketch와 다르게 지어내지 않는다. 근거가 없는 칸은 "없음"으로 쓴다.
- 확인 전에 push하거나 PR을 만들지 않는다.
