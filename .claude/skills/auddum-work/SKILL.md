# auddum-work

작업 하나(이슈 하나, 브랜치 하나)를 sketch를 기준으로 진행한다. **너(메인 스레드)가 오케스트레이터이고 구현도 한다.** 검증은 서브에이전트와 도구가 맡고, 사람은 목표·이슈 선택·sketch 승인·머지를 맡는다. 서브에이전트는 다른 서브에이전트를 띄울 수 없으므로 지휘는 여기서 한다.

이 파일은 라우터다. 절차는 `references/<라우트>.md`, 라우트가 같이 쓰는 것은 `references/shared/`에 있다. 필요한 라우트 파일만 읽는다.

## 라우팅

| 요청 | 라우트 | 파일 |
|---|---|---|
| 다음에 뭘 할지 | next | `references/next.md` |
| 이슈를 시작한다, sketch를 쓴다·승인받는다 | start | `references/start.md` |
| 작은 일(동작·규칙이 안 바뀜) | small | `references/small.md` |
| 테스트·구현·검증·리뷰 | build | `references/build.md` |
| 정본 갱신, 교훈, sketch 마무리 | wrap | `references/wrap.md` |
| PR을 연다 | pr | `references/pr.md` |
| PR 코멘트를 처리한다 | revise | `references/revise.md` |

small은 전용 커맨드가 없다. `/start`가 크기를 구분해 작은 일이면 small로 넘긴다.

요청이 둘 이상에 걸리면 앞 라우트부터 하나씩 한다. 한 번에 여러 라우트를 읽지 않는다(읽는 양을 줄이려고 나눈 것이다).

## 부분 재실행

"커밋해줘", "리뷰 다시", "이 테스트만 다시", "PR 본문만 다시"는 이렇게 처리한다.

- 재진입 판정으로 현재 단계를 정하고 그 라우트의 해당 단계로 보낸다.
- 단계 안 작업이 둘 이상이거나 모호하면 되묻는다.
- "설계 리뷰 다시"처럼 리뷰어 하나만 다시 부르는 요청은 새 라운드에서 그 리뷰어만 부르고, 합치기는 직전 라운드의 다른 리포트를 쓴다.

이유: 같은 말도 어느 단계에서 했느냐에 따라 뜻이 다르다.

## 크기 구분

시작할 때 "동작이나 규칙이 바뀌는가?"를 묻는다.

- 아니오 → **작은 일**: `chore/` 브랜치, sketch 없음, `./gradlew build`만, PR 본문에 "문서 영향 없음 + 이유".
- 예 → **일반 이슈**: 기능·리팩터링·버그 모두 같은 절차. 두 리뷰어를 모두 부른다.

동작·규칙이 안 바뀌는 오타·한 줄 수정은 이 구분을 거치지 않고 대화에서 바로 고친다. 브랜치·PR까지 요청하면 작은 일(small)로 받는다. 동작이 바뀌는 수정은 한 줄이어도 일반 이슈다. 애매하면 일반 이슈로 본다. 이유: 작게 보고 건너뛴 리뷰는 되돌리기 어렵고, 크게 본 비용은 시간뿐이다. 위험도 3단계는 쓰지 않는다. 버그는 별도 경로 없이 일반 이슈이고, 정본이 틀리고 코드가 맞으면 작은 일이다.

## 관문

앞 단계를 통과하지 못하면 다음 라우트로 넘어가지 않는다.

| 넘어가려면 | 확인 | 이유 |
|---|---|---|
| start → build | sketch `status`가 `승인됨` | 의도를 합의하기 전의 구현은 버려지기 쉽다 |
| build → wrap | `./gradlew build` 통과, 두 리뷰어 판정 FAIL 아님 | 도구가 최종 판정이다. 에이전트의 PASS는 build를 대신하지 않는다 |
| wrap → pr | 정본 갱신 커밋, fact-verifier 비FAIL, `status: 완료` | PR 본문은 완료된 sketch의 결과 칸에서 만든다 |

## 재진입 판정

세션이 끊겨도 이어받도록 상태는 대화가 아니라 파일에 있다. 이어받을 때 이 순서로 읽는다.

1. `git branch --show-current`: `feature/{이슈}-…` 또는 `chore/…`. `main`·`develop`이면 쓰기 작업을 하지 않는다.
2. `docs/records/sketches/`의 해당 이슈 sketch `status`: 초안 → start 중, 승인됨 → build, 완료 → pr·revise.
3. `_workspace/<run-id>/`: 테스트 노트와 리뷰 리포트가 있으면 build의 어디까지 했는지 알 수 있다.
4. `gh pr list --head <브랜치>`: PR이 있으면 revise.

읽은 결과를 한 줄로 사용자에게 알리고 해당 라우트로 간다. 상태가 서로 어긋나면(예: `승인됨`인데 PR이 열려 있음) 고르지 않고 사람에게 묻는다.

## 공통 규칙

- 사람 확인이 필요한 지점은 `references/shared/사람-확인-지점.md`가 정본이다. 이유: 외부에 보이는 행동은 되돌리기 어렵다.
- 머지는 사람만 한다. `develop`·`main`에 직접 커밋·push하지 않는다.
- 같은 실패는 **2회 재시도 후 중단**하고 미해결 항목을 보고한다. 이유: 기준을 낮춰 통과시키는 것을 막는다.
- 에이전트는 `Agent` 도구를 `name` 없이 호출한다(서브에이전트 모드). 이유: 이름을 붙이면 팀 모드로 호출되어 읽기 전용 에이전트 가정이 깨진다.
- 에이전트에게는 파일 경로를 주고 내용을 복붙하지 않는다. 이유: 입력이 갈라지지 않고 토큰이 준다.
- 에이전트 산출물(리뷰어는 최종 응답의 리포트)이 없으면 1회 재호출하고, 또 없으면 중단해 보고한다. 이유: 빈 결과로 다음 단계로 넘어가지 않는다.
- 에이전트가 이유를 지어내지 않는다. 출처가 없으면 질문으로 올리고 사람에게 그대로 전달한다.
- 리뷰 리포트는 전문을 사용자에게 보인다. 경로만 알리지 않는다.
- 새 규칙은 구현 중에는 sketch의 요구사항 칸이 기준이고, 정본은 wrap에서 확정된 것만 한 번에 갱신한다.
- 기준은 스킬이 아니라 docs에 있다. 코드가 정본과 다르면 코드를 고친다(이미 구현된 기능).

## 스킬을 나눌 신호

아래 중 하나라도 생기면 스킬을 나눈다.

- 한 라우트가 다른 라우트의 내용을 길게 설명한다.
- 이 파일이 150줄을 넘는다.
- 라우트가 열 개를 넘는다.
