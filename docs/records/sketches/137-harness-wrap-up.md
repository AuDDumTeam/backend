# 새 하네스(auddum-work)로 전환을 끝내고 옛 스킬을 걷어낸다

> 이슈 하나의 의도와 접근, 결과를 남기는 이력 문서다. 정본이 아니다. 끝나면 규칙은 정본으로 옮기고 여기에는 "왜 그렇게 했나"가 남는다.

## 요구사항과 규칙

새 하네스(`auddum-work` 스킬, 커맨드 6개, 에이전트 5개, hook 2개)가 갖춰졌다(#129~#136). 전환 기간에 둔 것들을 걷어내고 포인터를 맞춘다. 범위는 이슈 #137의 작업 목록이고 설계는 #99다.

소스와 달라진 점:

- 선행 이슈 중 #132(세션 재진입 시험)와 #134(`revise` 시험)가 열려 있다. 옛 스킬을 지우면 새 스킬만 남으므로, 삭제를 마지막 커밋으로 두고 그 두 시험은 다음 실제 작업에서 한다(질문 3).
- 이슈는 `CLAUDE.md`의 구현 주체 문장을 따로 말하지 않는다. #99의 확정 설계에 맞춰 바꾼다(질문 1).
- 자연어 발동의 범위를 정했다: 오타·한 줄 수정은 대화에서 바로 고치고, 커밋·리뷰 다시 같은 부분 재실행은 받는다(질문 4, 5).

| 규칙 | 어긋나면 | 근거·테스트 |
|---|---|---|
| 이슈 작업 요청(다음 할 일, 시작, 구현, 마무리, PR, 리뷰 반영)과 부분 재실행("커밋해줘", "리뷰 다시", "이 테스트만 다시", "PR 본문만 다시")은 자연어로도 `auddum-work`가 받아 가장 가까운 라우트로 보낸다 | 커맨드를 외워야만 하네스가 돌고, 옛 스킬이 받던 요청이 밖으로 떨어진다 | #99, 질문 5 · 새 세션에서 자연어 요청으로 확인 |
| 오타·한 줄 수정은 하네스를 켜지 않고 대화에서 바로 고친다. 브랜치·PR까지 요청하면 `small`이 받는다 | 사소한 수정에도 하네스가 켜져 무겁다 | 질문 4 · 새 세션에서 확인 |
| 옛 스킬(`auddum-team`, `auddum-code-review`, `auddum-conventions`)은 없다. 기준은 스킬이 아니라 docs에 있다 | 두 하네스가 같은 요청에 겹쳐 켜지고 기준이 두 곳에 있다 | #99 · 삭제 후 참조 검색 0건 |
| 구현은 sketch 승인 뒤 메인 스레드가 한다. 리뷰어와 test-writer는 구현 코드를 쓰지 않는다 | 구현 주체가 문서마다 다르다 | #99, 질문 1 |
| 커밋은 경로를 명시해 스테이징하고(`git add -A`·`git add .` 금지) `.env`와 `.env.*`(`.env.example`은 예외)는 절대 스테이징하지 않는다. `application-local.yaml`은 스테이징 전에 실제 값이 들어갔는지 본다 | 비밀 값이 커밋된다 | 옛 `auddum-team` 규칙을 옮김 · `git status` 확인 |
| 에이전트는 `name` 없이 `Agent` 도구로 부른다(서브에이전트 모드) | 팀 모드로 호출되어 읽기 전용 에이전트 모델이 깨진다 | 옛 `auddum-team` 규칙을 옮김, `settings.json`의 팀 모드 끔 |
| `.claude`와 `CLAUDE.md`에 `§` 참조를 두지 않고 ID와 문서 이름으로 가리킨다 | 문서 번호가 바뀌면 참조가 깨진다 | #137 · `grep` 0건 |

## 건드리는 것

- 고친다:
  - `CLAUDE.md`: 아래 접근 칸의 유지/이동/폐기 표대로 다시 쓴다
  - `.claude/skills/auddum-work/SKILL.md`: 자연어 발동을 켜고, 전환 설명과 라우팅 표의 "담당 이슈" 열을 지우고, 공통 규칙에 `name` 없이 호출·부분 재실행 처리·에이전트 산출물이 없을 때 1회 재호출을 더하고, description에 부분 재실행 발화를 더하며 끝의 경계 문구를 "오타·한 줄 수정은 대화에서 바로 고친다. 브랜치·PR 요청은 small"로 바꾼다
  - `.claude/skills/auddum-work/references/shared/사람-확인-지점.md`: 스테이징·비밀 값 규칙과 권한 설계 이유(`git add/commit/push`는 `allow`에 두지 않아 사람 확인 뒤에도 한 번 더 걸러진다)를 더한다
  - `.claude/skills/auddum-work/references/build.md`: 내장 `/code-review`는 필수가 아니고 사용자가 원할 때만 안내한다는 한 줄을 더한다
  - `.claude/skills/auddum-work/references/wrap.md`: 정본 갱신 때 낡은 서술("추가 예정" 같은 지난 표현, 바뀐 설정·경로·명령)을 찾는 점검을 더한다
  - `.claude/agents/test-writer.md`: 테스트 지원 클래스 규칙을 더하고 "강제는 hook(#136)이" 같은 전환기 표현을 지운다
  - `docs/engineering/컨벤션.md`: 테스트의 오류 메시지 구분(상태 위반은 오류 코드 메시지, 입력 검증 실패는 필드별 사유)을 더한다
  - `docs/howto/개발-워크플로.md`: 작은 일 표에 "오타·한 줄 수정은 대화에서 바로 고치고, 이슈 없이 PR로 남길 때 작은 일"을 맞춘다
  - `docs/index.md`: 문서 지도의 이력 행에 하네스 회고를 더한다
  - `docs/records/README.md`: 기록 표에 회고 행을 더한다
- 새로 만든다: `docs/records/하네스-회고.md`(하네스가 바뀐 이력, 후속 목록과 시작 신호. 교훈은 `pitfalls.md`를 링크만 한다)
- 지운다: `.claude/skills/auddum-team/`, `.claude/skills/auddum-code-review/`, `.claude/skills/auddum-conventions/`
- 건드리지 않는다: `V1__init_schema.sql`의 `§` 주석(Flyway 체크섬에 주석이 들어가 바꾸면 기존 DB 검증이 깨진다), 과거 sketch와 `_workspace`, 앱 코드

## 접근

작업 순서는 되돌리기 쉬운 것부터다. ① 새 체계로 옮길 것을 먼저 쓴다 ② 자연어 발동을 켠다 ③ 옛 스킬을 지운다. 삭제를 마지막 커밋으로 두면 PR 안에서 문제가 보일 때 그 커밋만 되돌릴 수 있다. 머지 뒤에는 squash라 한 커밋이므로, 자연어 발동 확인은 삭제 뒤 머지 전에 새 세션에서 마친다.

"`CLAUDE.md`는 포인터만" 이라는 표현은 정확히 "문서 지도와 변경 이력은 포인터만, 항상 지켜야 하는 최소 규칙은 요약으로 둔다"이다.

검토한 대안:

- 옛 스킬을 남겨 두고 설명만 "폐기됨"으로 바꾸기: 같은 요청에 겹쳐 켜지거나 오래된 기준이 읽힐 수 있다. 삭제한다.
- `V1__init_schema.sql`의 `§` 주석 고치기: 주석도 체크섬에 포함되어 이미 적용된 DB의 검증이 깨진다. 범위 밖이다.
- 후속 항목을 이슈로 지금 등록하기: 당장 하지 않을 이슈가 쌓여서 회고 문서에 목록만 남긴다(질문 2).
- `코드-리뷰-기준.md`에 줄어든 기술 세부를 되살리기: 점검표는 특정 기술·이름이 낡는다는 이유로 원칙과 이유로 쓰기로 했다. 되살리지 않는다.

질문과 답:

- 질문 1. `CLAUDE.md`의 구현 주체 규칙(기본은 사용자)을 #99의 새 설계(메인 스레드가 구현)에 맞춰 바꿔도 되는가? 답: 바꾼다(사용자, 2026-11-01).
- 질문 2. 마일스톤의 후속 목록은? 답: `하네스-회고.md`에 목록만 남기고 이슈는 만들지 않는다. 필요해지면 `/next`가 후보로 올린다(사용자, 2026-11-01).
- 질문 3. 옛 스킬 삭제 시점과 미시험 항목(#132, #134)은? 답: 삭제는 마지막 커밋으로 하고 미시험 항목은 삭제 뒤 다음 실제 작업에서 시험한다(사용자, 2026-11-01).
- 질문 4. 오타·한 줄 수정을 하네스가 받는가? 답: 대화에서 바로 고친다. 브랜치·PR이 필요하면 `small`이 받는다(사용자, 2026-11-01).
- 질문 5. "커밋해줘", "리뷰 다시" 같은 부분 재실행을 자연어로 받는가? 답: 받는다. 가장 가까운 라우트 단계로 보낸다(사용자, 2026-11-01).

- 질문 6. `코드-리뷰-기준.md`에서 기술 세부(엔티티 직접 노출, `@Modifying`, 로그 레벨 등)를 뺀 것은 의도된 폐기인가? 답: 의도된 폐기다. 코드 리뷰 기준을 쓸 때 사용자가 "OOP, DDD, 의존성, 책임, 역할, 협력 위주로 보면 되고, 특정 기술·클래스·메서드 이름은 낡는다"고 지시했다(사용자, 2026-11-01, #127). sketch 승인 때 다시 확인받았다(사용자, 2026-11-01).

- 질문 8. PR은 `Closes`인가 `Refs`인가? 답: 이슈 완료 기준에 `/revise`가 새 스킬로 동작한다는 항목이 있고 `revise`를 아직 시험하지 못했다. `Refs #137`로 올리고, `revise` 시험이 끝나면 사용자 확인을 받아 닫는다(사용자 승인, 2026-11-01).

## 안전장치

- 자연어 발동이 너무 넓으면 개념 질문이나 한 줄 수정에도 하네스가 켜진다. description의 경계 조건과 `CLAUDE.md`의 비발동 규칙으로 막고 새 세션에서 확인한다.
- 옛 스킬 삭제 뒤 새 스킬이 안 돌 때 돌아갈 곳이 없다. 삭제를 마지막 커밋으로 두고 머지 전에 확인한다. 머지 뒤 문제가 생기면 삭제된 파일을 git 기록에서 되살린다.
- `CLAUDE.md`를 줄이다가 지켜야 할 규칙이 빠질 수 있다. 위 처리 표대로 하나씩 옮기고, 끝난 뒤 옛 `CLAUDE.md`와 대조한다.
