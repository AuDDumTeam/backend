# sketch 양식을 하네스 설계에 맞춰 고친다

## 요구사항과 규칙

하네스(라우트·에이전트)가 sketch를 읽고 쓰고 검사하므로, 그 기준이 되는 양식을 먼저 정한다. 이슈 #127은 문서 7가지를 정비하고, 사용자와 합의해 PR 2개로 나눴다. 이 sketch는 그중 첫 번째(sketch 양식)를 다루고, 새 양식으로 쓴 샘플을 겸한다.

소스와 달라진 점: #127은 `docs-check`가 새 `status` 값(초안·승인됨)을 허용하도록 고치라고 했다. 확인해 보니 `docs-check`는 `status` 값을 검사하지 않아서 고칠 곳이 없다. `status` 검사는 CI 문서 관문 이슈(#128)에서 새로 넣는다.

| 규칙 | 어긋나면 | 근거·테스트 |
|---|---|---|
| sketch의 `status`는 `초안` → `승인됨` → `완료` 순서로 바뀐다 | 검사는 #128에서 넣는다 | `sketches/README.md` |
| 칸 제목은 한글만 쓴다 | 리뷰에서 고친다 | `_양식.md` |

## 건드리는 것

- 고친다: `records/sketches/_양식.md`, `records/sketches/README.md`
- 새로 만든다: 이 sketch(새 양식 샘플)
- 하지 않는다: `scripts/DocsCheck.java`(위 이유), 기존 sketch(소급 없음), 개발 워크플로 문서의 시작 절차(2번째 PR)

## 접근

머리말에 `sources`를 더하고 `status`의 값을 바꾼다. 칸은 설계 합의의 8칸(요구사항과 규칙 / 건드리는 것 / 접근 / 구조 / 순서와 테스트 / 지킬 규칙 / 안전장치 / 결과)으로 한다. 요구사항 칸의 규칙 표는 정본 규칙 표(`규칙 / 어긋나면 / 근거·테스트`)와 같은 모양이라 끝나면 그대로 옮긴다.

버린 안: `docs-check`에 `status` 값 검사를 이번에 함께 넣는 안. 소급하지 않는다는 조건과 CI 관문 이슈(#128)의 범위가 겹쳐서 미뤘다.

질문과 답: PR을 한 개로 할지 나눌지 물었고, 2개로 나누기로 했다(사용자, 2026-11-01).

## 구조

양식은 `docs/records/sketches/_양식.md`, 사용법은 같은 폴더의 `README.md`에 둔다. `_`로 시작하는 파일은 `docs-check`가 검사하지 않는다.

## 순서와 테스트

1. `_양식.md`를 새 칸과 머리말로 바꾼다.
2. `README.md`에 머리말·상태·소급 규칙을 적는다.
3. 이 sketch를 새 양식으로 쓴다.
4. `scripts/docs-check`로 샘플이 통과하는지 본다.

## 지킬 규칙

- 표기 규칙: `docs/index.md`
- 참조는 ID로만 하고 § 번호를 쓰지 않는다.

## 안전장치

양식만 바꾸면 기존 sketch가 깨질 수 있다. `docs-check`가 `status`와 칸 제목을 검사하지 않으므로 기존 파일은 그대로 통과하고, 소급하지 않는다고 README에 적었다.

## 결과

양식과 README를 고치고 샘플을 만들었다. `scripts/docs-check`로 확인한다.

계획과 달라진 점: `docs-check` 수정은 필요 없어서 하지 않았다.

한계와 후속: `status` 값과 칸 제목 검사는 #128에서 넣는다. 나머지 정비(pitfalls, 코드 리뷰 기준, 개발 워크플로, 이슈·PR 양식)는 다음 PR에서 한다.
