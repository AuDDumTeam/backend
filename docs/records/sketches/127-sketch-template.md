# 하네스가 읽는 문서(sketch 양식·교훈·코드 리뷰 기준·워크플로·이슈 양식)를 정비한다

## 요구사항과 규칙

하네스(라우트·에이전트)가 sketch를 읽고 쓰고 검사하고, 코드 리뷰 기준과 이슈·PR 양식을 따른다. 그 기준이 되는 문서를 라우트와 에이전트보다 먼저 정한다. 기준은 스킬이 아니라 docs에 둬서 개발자와 AI가 같은 기준을 본다. 이슈 #127은 문서 7가지를 정비하고, 사용자와 합의해 PR 2개로 나눴다. 이 sketch는 새 양식으로 쓴 샘플을 겸한다.

소스와 달라진 점:

- #127은 `docs-check`가 새 `status` 값(초안·승인됨)을 허용하도록 고치라고 했다. 확인해 보니 `docs-check`는 `status` 값을 검사하지 않아서 고칠 곳이 없다. `status` 검사는 CI 문서 관문 이슈(#128)에서 새로 넣는다.
- #127은 이슈 양식을 요청서와 버그 두 가지로 적었다. 하나로 줄였다(아래 접근).
- `auddum-conventions`는 대부분 `index.md`·컨벤션에 이미 있어서 옮기지 않고 없던 것만 흡수했다.

| 규칙 | 어긋나면 | 근거·테스트 |
|---|---|---|
| sketch의 `status`는 `초안` → `승인됨` → `완료` 순서로 바뀐다 | 검사는 #128에서 넣는다 | `sketches/README.md` |
| 칸 제목은 한글만 쓴다 | 리뷰에서 고친다 | `_양식.md` |
| 코드 리뷰는 원칙과 이유로 쓰고 특정 클래스·메서드 이름을 적지 않는다 | 이름이 코드와 어긋나 낡는다 | `코드-리뷰-기준.md` |

## 건드리는 것

- 고친다: `records/sketches/_양식.md`와 `README.md`, `howto/개발-워크플로.md`, `engineering/테스트-전략.md`, `index.md`, `.github/pull_request_template.md`
- 새로 만든다: `records/pitfalls.md`, `records/README.md`, `engineering/코드-리뷰-기준.md`, `.github/ISSUE_TEMPLATE/요청서.md`, 이 sketch
- 하지 않는다: `scripts/DocsCheck.java`(위 이유), 기존 sketch(소급 없음), 옛 스킬(`auddum-code-review`, `auddum-conventions`) 삭제와 에이전트가 새 문서를 읽게 하는 연결(#130, #137)

## 접근

머리말에 `sources`를 더하고 `status`의 값을 바꾼다. 칸은 설계 합의의 8칸으로 한다. 요구사항 칸의 규칙 표는 정본 규칙 표와 같은 모양이라 끝나면 그대로 옮긴다.

코드 리뷰 기준은 옛 스킬을 옮기기만 하면 낡은 점이 있어 다시 썼다. 도메인 리뷰(정책·문서와 맞는지)와 코드 리뷰(설계·품질)로 나누고, 코드 리뷰는 의존, 책임·역할, 협력, OOP, DDD를 점검표로 삼았다. 컨벤션과 보안은 매번 같이 본다.

버린 안:

- `docs-check`에 `status` 값 검사를 이번에 함께 넣는 안. 소급하지 않는다는 조건과 CI 문서 관문 이슈(#128)의 범위가 겹쳐서 미뤘다.
- 점검표에 프로젝트 규칙을 전문으로 옮기는 안. 설계-결정이 같은 규칙을 두 곳에 두지 말라고 하고, 어긋난다.
- 점검표에 `Vote`와 `Report`처럼 특정 이름을 적는 안. 그 이름이 나온 곳만 보게 되고 코드가 바뀌면 낡는다. 원칙과 이유로 썼다.
- 상태 확인 누락 전용 판정 ID. 방법(메서드)에 묶여 낡고 협력 표와 도메인 리뷰가 이미 잡는다.
- 이슈 양식 두 개. 버그는 요청서에 정본 동작과 실제 동작, 재현 방법만 더하면 되고 1인 개발에서 양식을 나눌 만큼 쓰는 일이 많지 않다.

질문과 답:

- PR을 한 개로 할지 나눌지: 2개로 나눈다(사용자, 2026-11-01).
- 코드 컨벤션 위반의 수준: 차단(사용자, 2026-11-01).
- 코드 리뷰 사례의 출처: 과거 리뷰 리포트(사용자, 2026-11-01). 이름은 낡으므로 모양만 남겼다.
- 점검표의 모양: 이름 대신 원칙과 이유(사용자, 2026-11-01).
- 이슈 양식: 요청서 하나로 줄인다(사용자, 2026-11-01).

## 구조

양식은 `docs/records/sketches/_양식.md`, 사용법은 같은 폴더의 `README.md`에 둔다. 교훈은 `docs/records/pitfalls.md`, 코드 리뷰 기준은 `docs/engineering/코드-리뷰-기준.md`다. 이슈·PR 양식은 `.github/`에 둔다.

## 순서와 테스트

1. PR 1: `_양식.md`와 `README.md`를 고치고 이 sketch를 새 양식으로 쓴다. `scripts/docs-check`로 샘플이 통과하는지 본다.
2. PR 2: 교훈, 코드 리뷰 기준, 개발 워크플로, 테스트 전략, 이슈·PR 양식을 쓴다.
3. 매번 `scripts/docs-check`, `scripts/test-docs-check`, `./gradlew build`를 돌린다.

## 지킬 규칙

- 표기 규칙: `docs/index.md`
- 참조는 ID로만 하고 § 번호를 쓰지 않는다.
- 같은 규칙을 두 문서에 옮겨 적지 않는다.

## 안전장치

양식만 바꾸면 기존 sketch가 깨질 수 있다. `docs-check`가 `status`와 칸 제목을 검사하지 않으므로 기존 파일은 그대로 통과하고, 소급하지 않는다고 README에 적었다.

## 결과

PR 1에서 sketch 양식과 샘플을 만들었고, PR 2에서 교훈, 코드 리뷰 기준, 워크플로(작은 일과 일반 이슈 구분, `chore/*` 브랜치, 커밋 단위, Draft PR), 이슈 양식, PR 템플릿을 정비했다. 테스트 전략에는 없던 두 방침(한 테스트는 규칙 하나, 저장소 쿼리 단독 테스트 금지)을 더했다. 완료 기준을 충족했다: `scripts/docs-check`가 통과하고, 새 양식으로 쓴 이 sketch가 검사를 통과하고, 코드 리뷰 기준을 스킬 없이 docs에서 읽을 수 있다.

계획과 달라진 점:

- `docs-check` 수정은 필요 없어서 하지 않았다.
- 이슈 양식을 두 개에서 하나로 줄였다.
- 코드 리뷰 기준은 옛 스킬을 그대로 옮기지 않고 다시 썼다.
- 코드 리뷰 기준의 상태 확인 누락 전용 판정 ID를 두지 않았다.

한계와 후속:

- 에이전트(`code-reviewer`, `domain-reviewer`)는 아직 옛 스킬을 읽는다. 새 문서를 읽게 하는 연결은 #130에서 한다. 그 전까지 스킬과 `코드-리뷰-기준.md`에 같은 내용이 있다.
- 옛 스킬(`auddum-code-review`, `auddum-conventions`) 삭제는 #137에서 한다.
- `status`와 칸 제목 검사, PR 필수 칸 검사는 #128에서 한다.
- 이슈 양식을 GitHub 화면에서 렌더링해 확인하지 못했다. 머지 뒤 새 이슈 화면에서 본다.
