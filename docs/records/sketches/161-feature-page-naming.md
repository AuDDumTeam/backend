# 기능 페이지 이름 원칙을 정하고 7개 이름을 점검한다

> 이슈 하나의 의도와 접근, 결과를 남기는 이력 문서다. 정본이 아니다. 끝나면 규칙은 기능 페이지와 도메인 문서로 옮기고 여기에는 "왜 그렇게 했나"가 남는다.

## 요구사항과 규칙

`02-투표-만들기`는 작성자의 투표 삭제(UC-17, R-POLL-09·13·16·17)까지 맡는데 이름이 삭제를 드러내지 않아, 삭제 규칙을 찾는 사람이 이 페이지를 떠올리기 어렵다. 이름 방식을 한 번 정하고 7개 페이지를 그 원칙으로 점검한다(#76 작업 중 짚였고 범위를 지키려고 분리). 문서 작업이라 동작과 규칙(R·P·UC)은 바뀌지 않는다.

소스와 달라진 점: 없음.

현재 7개 페이지(확인한 것):

| 페이지 | 맡은 UC | 점검 메모 |
|---|---|---|
| 01-둘러보기 | UC-01·02 (목록·상세 조회) | 맞다 |
| 02-투표-만들기 | UC-07·08·09 + UC-17(삭제) | 삭제가 이름에 없다. 어긋남이 가장 크다 |
| 03-참여하기 | UC-03·04·10·11·12 | 맞다 |
| 04-결과-보기 | UC-13 하나, 자체 API 없음 | 이름은 맞지만 페이지가 얇다. 커질 일은 로드맵에 없다 |
| 05-신고하기 | UC-14 | 맞다 |
| 06-관리자-조치 | UC-15 + OP-01~10 | #20으로 복구·정지 해제가 붙으면 "조치"에 들어가는지 본다 |
| 07-로그인과-회원 | UC-05·06·16 | 맞다 |

로드맵(`product/로드맵.md` M1~M7, PRD 9절)에는 작성자용 "내 투표 목록·결과" 같은 기능이 없다. PRD는 작성자가 할 수 있는 일을 삭제뿐이라고 적는다(PRD 86행).

## 건드리는 것

- 건드린다: `docs/features/README.md`(원칙 한 줄), 이름을 바꾸기로 한 페이지 파일과 그 다이어그램(`docs/diagrams/NN-….d2·svg`), 링크가 걸린 `docs/index.md`·`docs/generated/API-목록.md`·옛 sketch 3개.
- `API-목록.md`는 생성 문서다. `ApiListRenderer`가 `docs/features/`의 `NN-….md` 파일 이름에서 링크를 만들기 때문에 고칠 코드는 없고, 페이지를 옮긴 뒤 다시 생성만 하면 된다(`DOCS_UPDATE=1 ./gradlew test --tests '*OpenApiDocTest'` 계열, 정확한 테스트는 구현 때 확인). `./gradlew build`가 생성 결과를 비교한다.
- 02 페이지 안: H1(`# 투표 만들기`), 이미지·원본 링크 두 곳. `docs/index.md`는 65행 기능 지도 행 하나(링크 텍스트와 경로). 다이어그램 `02-….d2` 18행의 라벨 `투표 만들기 요청`과 SVG에 구워진 글자는 그대로 둔다(질문 4).
- 옛 sketch 3개(76, 109-feature-pages-2, 114-openapi-json)는 이력 문서라서 경로 형태의 참조만 새 이름으로 바꾸고 서술형 언급은 둔다(질문 5). `_workspace/`는 대상이 아니다.
- 안 건드린다: `src/main` 동작, R·P·UC 번호와 내용.

## 접근

원칙 후보는 이슈의 두 가지다.

- (a) 사용자 행동 이름(지금): 둘러보기·만들기·참여하기. 스토리맵 순서와 맞고 읽는 사람이 "내가 하려는 일"로 찾는다.
- (b) 상위 개념 명사: 투표 탐색·내 투표·참여·결과·신고·관리자 조치·회원. 기능이 붙어도 이름이 유지된다.

결정(사용자, 2026-11-02): (a)를 유지하고 "페이지 이름은 그 페이지가 맡은 UC를 모두 떠올리게 한다"를 원칙으로 둔다. 혼합 페이지 기준은 아래와 같다.

- 같은 행위자가 같은 대상에 하는 일은 한 페이지에 두고, 이름이 그 일을 모두 드러낸다(`A와-B`, 선례 `07-로그인과-회원`).
- 행위자가 다르거나, 규칙·생애주기가 갈리거나, 한 번에 읽기 어려울 만큼 커지면 쪼갠다.
- 이름 하나로 다 담기지 않으면 너무 섞였다는 신호로 본다.

근거: 로드맵에 작성자 기능 확장이 없어 (b)의 장점(확장 시 유지)이 지금은 쓰이지 않고, 다른 6개는 이미 (a)에 맞는다는 점이다. 이름을 바꾸는 것은 02 하나이고, 04·06은 두고 이유를 README에 적는다.

## 구조

- 원칙은 `docs/features/README.md`의 파일 이름 행 근처에 한 줄로 쓴다.
- 이름을 바꾸면 `git mv`로 페이지와 `docs/diagrams/02-….d2·svg`를 옮기고, 다이어그램 안의 이미지·원본 링크를 고친다.

## 순서와 테스트

1. 질문 1~5에 답을 받아 이 sketch에 적는다.
2. 이름을 바꾼다면: 페이지와 다이어그램 파일 이동, `docs/index.md`·옛 sketch 링크 수정, `API-목록.md`는 코드 수정 없이 다시 생성.
3. `docs/features/README.md`에 원칙 한 줄을 적는다.
4. 확인: `./gradlew build`(생성 문서 비교 포함)와, `02-투표-만들기`를 grep해서, 남은 곳이 옛 sketch 3개의 문장 속 언급(허용 목록)뿐인지 본다. 머리말 값과 `.md`·`.svg`·`.d2` 경로, 현재 문서에는 남으면 안 된다. `_workspace/`는 제외. 이 작업은 동작을 바꾸지 않아 새 테스트(red)는 없다.

## 지킬 규칙

- 정본은 기능 페이지 하나다(`docs/index.md`). 이름을 바꿔도 내용은 옮기지 않는다.
- 문서만 고친 작업은 이력을 적지 않고 `features: [없음]`이다(`개발-워크플로.md` wrap 표, `features/README.md` 이력 행). 그래서 이 sketch는 02의 이력 표에 넣지 않는다.

## 안전장치

- 깨진 링크: 옛 이름 전체 검색으로 확인한다(문서, 다이어그램, 생성 문서, 옛 sketch의 경로 참조).
- 생성 문서 재생성을 빠뜨리면 `./gradlew build`가 실패한다. 페이지를 옮긴 직후 재생성하고 build로 확인한다.

## 결과

`docs/features/02-투표-만들기.md`를 `02-투표-만들기와-삭제.md`로 바꾸고(H1 포함) 다이어그램 `.d2`·`.svg`는 파일 이름만 옮겼다. `docs/index.md` 기능 지도 행, 재생성한 `API-목록.md`(링크 2곳), 옛 sketch 76의 머리말과 경로 참조를 새 이름에 맞췄다. `docs/features/README.md`에 이름 원칙 행을 더했다. 내용은 이름을 사용자 행동으로 짓고 UC를 모두 떠올리게 한다는 것, 같은 행위자·대상의 일은 한 페이지에 `A와-B`로 쓴다는 것, 쪼개는 조건, 이름 하나로 안 담기면 너무 섞였다는 신호라는 것, 04는 그대로이고 06은 #20 때 다시 본다는 것이다. 동작과 코드는 바뀌지 않았다.

계획과 달라진 점: 계획에는 `API-목록.md`를 만드는 코드를 고치는 단계가 있었지만, sketch-reviewer r1이 짚은 대로 `ApiListRenderer`가 파일 이름에서 링크를 만들어서 재생성만 했다. 이 sketch 자신의 `sources` 경로도 새 이름으로 맞췄다. code-reviewer는 코드 변경이 없어서 사용자 결정으로 부르지 않았다. 리뷰: sketch-reviewer r1 FAIL → r2 PASS_WITH_FIXES, domain-reviewer r1 PASS, fact-verifier r1 PASS_WITH_FIXES → r2 PASS.

한계와 후속: 06은 #20으로 복구·정지 해제가 붙을 때 이름이 맞는지 다시 본다. 109와 114 sketch의 문장 속 옛 이름은 이력이라 그대로 뒀다. 시작 단계에서 크기 구분(일반 이슈/small)을 사용자에게 말하지 않고 넘어갔다. 이는 하네스 절차의 개선 후속이다.
