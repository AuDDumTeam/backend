# 내가 참여한 투표 목록과 내가 올린 투표 목록 API를 만든다

> 이슈 하나의 의도와 접근, 결과를 남기는 이력 문서다. 정본이 아니다. 끝나면 규칙은 기능 페이지와 도메인 문서로 옮기고 여기에는 "왜 그렇게 했나"가 남는다.

## 요구사항과 규칙

회원이 자기가 참여한 투표와 올린 투표를 다시 볼 방법이 없다. 두 목록 모두 응답에 전체 개수 `totalCount`를 함께 줘서 화면이 개수를 바로 보여 준다(이슈 #163).

### 소스와 달라진 점

- 이슈가 sketch에서 정하라고 남긴 것(경로, 페이징, 정렬, 숨김·삭제 포함, `totalCount` 범위, 탈퇴·정지 회원 처리)을 아래 질문으로 올렸다. 정본에는 둘 다 아직 없다(`07-로그인과-회원.md`의 API 표에도 없다).
- `01-둘러보기.md` L37의 "목록에는 공개 투표만 나온다"와 P-07의 노출 항목(질문·카테고리·참여 수·마감 여부·생성 시각)은 범위 한정이 없다. Q2에서 올린 목록에 숨김 투표를 넣거나 `status`를 더하면 이 문장을 "공개 목록(`GET /polls`)에는 공개 투표만 나오고, 내가 올린 목록에는 …"으로 한정해 고쳐야 한다. 올린 목록에서 삭제 투표를 빼는 선택(Q2-A)은 R-POLL-18·UC-17(작성자는 삭제 투표도 조회할 수 있다)과 목록에서만 달라지는 규칙이 되므로 근거를 답에 적는다.

## 건드리는 것

- API: 목록 두 개(`GET /polls/mine`, `GET /polls/voted`). 응답은 `items`, `nextCursor`, `totalCount`다. `items`의 한 줄은 `GET /polls`의 `PollSummaryResponse`와 같다(질문, 카테고리, 참여 수, 마감 여부, 마감 시각, 생성 시각)에 올린 목록만 `status`를 더한다.
- 코드(예상): `poll` 쪽에 조회 두 개(`PollQueryService`, `PollReader`, `PollJpaRepository`)와 응답 DTO. 참여 목록은 참여 기록이 `vote` 도메인에 있어서 `ParticipationReader`처럼 `poll`이 포트를 선언하고 `vote`가 구현한다(아키텍처 '조회 조합'의 첫 행, 의존 방향 `vote → poll`을 지킨다, Q7).
- DB: 스키마는 안 바뀐다. `poll.author_id`와 `vote.member_id`는 외래키라 MySQL이 인덱스를 자동으로 만든다(V1 DDL에는 인덱스가 따로 보이지 않고, 테스트 H2와 운영 MySQL이 같은지는 측정 이슈로 미룬다). 조회 최적화 인덱스는 측정 뒤로 미룬다는 방침(`ERD.md` §5)을 따른다.
- 문서: `01-둘러보기.md`(규칙·사용하는 API·이력), `03-참여하기.md`(사용하는 API 한 줄), `07-로그인과-회원.md`(사용하는 API 한 줄), 생성 문서(`openapi.json`, `API-목록.md`), `로드맵.md`(M2 또는 M4에 #163 항목), `ERD.md` §6 쿼리 모양에 한 줄(필요하면).
- 안 건드리는 것: `GET /polls`와 `GET /polls/{pollId}`, 참여·삭제 규칙, 인증 필터, 다른 사람의 목록 조회(본인만).

## 접근

두 목록은 모양이 같아 한 이슈로 묶되, PR은 나눌 수 있다(Q8). 목록의 주체가 투표라서 조회는 `poll`의 사용 사례로 두고, 참여 기록은 포트로 받는다(`GET /polls`의 참여 수와 같은 방식, 새 의존을 만들지 않는다). 페이징은 기존 `PollCursor`(id 기준 커서)와 같은 모양을 쓴다.

검토한 대안: 기존 포트 `ParticipationReader`에 메서드 더하기(그 포트의 계약은 "요청한 모든 투표 ID를 키로 가진 맵"이라 "회원의 참여 투표를 순서대로"와 모양이 달라 새 포트 `ParticipatedPollReader`를 두는 쪽이 계약이 분명하다. 설계-결정의 포트 범위는 "필요가 생길 때만 늘린다"이다), `vote`가 목록을 소유하고 `PollReader`로 투표를 가져오기(`vote → poll` 방향은 맞지만 목록 응답 모양이 `poll`의 `PollSummary`라 `vote`가 poll의 응답 조립을 알게 된다), 조합 전용 서비스(facade)로 풀기(패키지와 ArchUnit 허용 맵 변경이 필요해 두 목록에는 과하다).

## 순서와 테스트

테스트는 계층(`테스트-전략.md`)별로 무엇을 보는지 나눈다. 이미 있는 테스트 클래스(`PollQueryServiceTest`, `PollListWebApiTest`, `PollListCategoryChainTest`, `VoteReaderTest`)는 먼저 읽고 케이스를 더한다(pitfalls #162). 동작을 바꾸지 않는 새 API라 기존 기대값은 바뀌지 않지만, 시작 때 `grep`으로 `PollSummary`·`PollQueryService`를 쓰는 테스트를 세어 영향이 없는지 확인한다.

1. **올린 목록**(Q8-B의 첫 PR, `Refs #163`)
   - 서비스 통합(H2): 본인 투표만 나온다, 다른 작성자 것은 안 나온다, 숨김·삭제 처리(Q2), 최신순, 커서로 이어진다, 마지막 쪽 `nextCursor` null, `totalCount`, 정지 회원 조회 가능, 탈퇴 401, 없는 회원 404(Q5).

   - 체인(대표 한 건): 로그인한 회원이 투표를 만든 뒤 목록에 나온다, 비로그인은 401.

## 지킬 규칙

- P-01: 숨김·삭제된 투표는 일반 사용자에게 없는 것처럼 보인다. R-POLL-18: 작성자와 관리자는 상태와 함께 본다.
- R-MEMBER-11: 정지 회원은 조회·로그아웃·탈퇴·재발급만 한다(Q5).
- 도메인 사이 의존: `vote → poll`만 허용이고 `poll`은 `vote`를 쓰지 않는다. 서비스는 `*JpaRepository`와 다른 서비스에 의존하지 않는다(ArchUnit).
- 표기 규칙: 조회 이름 `get`/`find`/`findAll`, record 파라미터 둘 이상이면 한 줄에 하나, 기본 package-private, 값 객체는 내부 값을 꺼내 넘기지 않는다.
- 테스트 메서드 이름은 한글이고 `@DisplayName`을 쓰지 않는다.

## 안전장치

- 다른 회원의 투표가 섞이면 안 된다. 회원 ID는 토큰에서만 받고 쿼리 파라미터로 받지 않는다. 다른 회원의 투표를 심어 둔 테스트로 확인한다.
- 비회원 참여와 회원 참여가 한 테이블(`vote`)에 있다. `member_id`가 NULL인 행을 절대 섞지 않도록 `member_id` 기준으로만 찾는다(`ck_vote_voter`).
- `totalCount`와 `items`의 필터가 어긋나면 화면이 틀린 개수를 보인다. 같은 조건을 한 곳에서 만들고, 개수와 목록 길이가 맞는 테스트를 둔다.
- 참여가 많은 회원의 전체 읽기(Q7-A)와 요청마다 count 쿼리(Q4-A)는 측정 전이라 수치를 주장하지 않는다. 느려지면 조회 최적화 인덱스와 쿼리 조인(Q7-B)을 따로 이슈로 정한다.

### 계획과 달라진 점

- **회원 확인**: sketch Q5는 `MemberReader.getNotWithdrawnMember`로 적었으나, 반환값을 버리는 `get` 호출이 어울리지 않아 `MemberValidator.validateNotWithdrawn`(반환값 없음)을 새로 만들어 썼다(사용자 지시). 응답은 같다.
- **페이징 인자**: `PollListRequest`로 묶었다가 풀어 넘기던 것을 사용자 지적으로 `CursorPaging.of(PollCursor.idOf(cursor), size)`로 바꿨다. 이 때문에 `PollCursor`를 `public`으로 열었다(컨트롤러가 `api` 패키지, `PollCursor`가 `api.dto` 패키지).
- **쪽 크기 상수**: `CursorPaging.clampSize`로 모았고 `PollListRequest.pageSize()`가 위임한다.
- **테스트**: test-writer가 쓴 체인 테스트가 쓰기 요청에 Origin 헤더를 빠뜨리고 `throws Exception`을 빠뜨려 메인이 고쳤다.
