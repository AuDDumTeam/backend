# 하네스 회고

하네스(`CLAUDE.md`, `.claude/`의 스킬·에이전트·hook, `scripts/hooks/`)가 어떻게 바뀌어 왔는지 남기는 곳이다. 지금 유효한 규칙의 정본이 아니다. 지금의 구성은 `CLAUDE.md`와 `.claude/skills/auddum-work/SKILL.md`를 본다.

## 지금의 하네스

2026-11-01에 #99 개편으로 `auddum-work` 하나가 라우터가 되고 에이전트 5개와 hook 2개가 갖춰졌다. 구성은 `CLAUDE.md`를 본다. 설계 합의와 단계별 기록은 이슈 #99와 각 sketch(`records/sketches/`)에, 겪은 함정은 [교훈](pitfalls.md)에 있다.

## 변경 이력

이전에 `CLAUDE.md`에 있던 변경 이력이다. 나오는 옛 스킬·파일·절차(확인 ①, git-workflow 등)의 이름은 당시의 것이다.

- 2026-11-01 — 이슈 #137. 새 하네스(`auddum-work`)로 전환을 마무리했다. 옛 스킬 `auddum-team`, `auddum-code-review`, `auddum-conventions`를 지우고 `CLAUDE.md`를 포인터와 최소 규칙 중심으로 줄였다. 구현 주체는 새 설계대로 메인 스레드다.
- 2026-11-01 — 문서 검사 도구 `DocsCheck`(`scripts/docs-check`)와 CI의 문서 검사 단계를 지웠다. CI가 막은 적이 없고 개편이 끝나 유지 이점이 작다고 판단했다. 생성 문서는 `./gradlew build`가 계속 비교한다. 필요하면 git 기록에서 되살린다. 이에 따라 #128(CI 문서 관문)을 닫고 #136의 커밋 전 docs-check hook 항목을 뺐다.
- 2026-10-22 — 이슈 #72. 정책·컨벤션 인터뷰 결과를 반영했다. 구현 주체는 이슈마다 확인 ①에서 정한다. 위험도에 변경 성격 축(구조 변경은 보통 이상)을 더했다. 두 리뷰어는 읽기 전용으로 바꾸고(Write 제거) 리포트는 오케스트레이터가 저장한다. 재리뷰는 동작·검증이 바뀐 경우에만 한다. 큰 이슈는 마지막 PR만 `Closes`로 나눈다. 정본 규칙은 `docs/howto/개발-워크플로.md`, `docs/engineering/컨벤션.md`, `docs/engineering/설계-결정.md`에 있다.
- 2026-10-18 — 이슈 #54. 설계·품질을 보는 code-reviewer를 추가했다(높음 위험도, domain-reviewer 뒤). 에이전트는 역할과 프로토콜만, 점검 항목과 예시는 `auddum-code-review` 스킬에 뒀다. 다른 docs에 없는 확정 결정과 코드 관행은 `docs/engineering/설계-결정.md`에 모아 리뷰어가 다시 지적하지 않게 했다(이미 있는 규칙은 옮기지 않고 포인터만 뒀다). 내장 `/code-review`는 필수에서 선택으로 바꿨다.
- 2026-10-13 — M1 문서 동기화. 이슈 #1·#2·#3·#7·#8을 병합한 뒤 개발 워크플로·로컬 환경 문서(PR 템플릿·CI·포맷·로컬 환경·의존성), 배포 문서(프로파일), git-workflow(`application-local.yaml` 커밋 허용)를 실제 구현에 맞췄다. 앞으로 이슈를 끝낼 때 같은 PR에서 어긋난 문서를 함께 고친다.
- 2026-10-12 — 이슈 #26. 팀의 역할을 테스트 작성과 리뷰로 한정했다(구현·도메인 모델 코드·마이그레이션은 사용자). 토큰 예산 때문에 작게 시작했다: 에이전트 2(test-writer, domain-reviewer), 오케스트레이터 1, 지원 스킬 1. (당시에는 코드 리뷰어를 만들지 않고 고위험 이슈에서 내장 `/code-review`를 쓰기로 했으나 #54에서 code-reviewer를 추가했다.) elcom-server 하네스의 구조(산출물 계약, 고정 지점, 책임 분리)를 줄여서 따랐다.

## 후속 (이 개편 밖)

이슈로 만들지 않고 여기에 목록과 시작 신호만 둔다. 필요해지면 `/next`가 후보로 올린다.

| 후속 | 시작 신호 |
|---|---|
| 에이전트 골든 케이스 테스트 | 리뷰어·검증자의 판정이 사람 판단과 자주 어긋날 때 |
| 규칙 표의 "상황 / 요청 / 기대 결과" 칸 검토 | 테스트가 규칙 표와 어긋난 것을 반복해서 발견할 때 |
| CI에서 에이전트 실행(이슈 라벨 → PR) | 로컬 세션 없이 작업을 시작하고 싶을 때 |
| 상시 갭 탐지 | `/next`의 후보가 낡은 정본을 놓치는 일이 생길 때 |
| 테스트·메인 설정 파일 동기화 확인 | 설정을 두 파일에 복제한 곳이 늘어날 때(#155 참고) |
| `revise`와 세션 재진입 시험 | 다음 실제 PR 코멘트와 새 세션에서 시험하고 틈이 나오면 고친다(#132, #134) |
| `컨벤션.md`의 `UnitTestSupport` | 코드에 없는 클래스를 문서가 적고 있다(#137 리뷰에서 발견). 문서나 코드 중 하나를 맞출 때 |
