# 교훈

일하다 겪은 함정과 대응을 짧게 남기는 곳이다. 정본이 아니다.

- 항목은 **제목 / 상황 / 대응 / 관련(ID·이슈)** 네 줄로 쓴다.
- 정본(기능 페이지·도메인 모델·컨벤션)이 주인이다. 규칙으로 정할 만하면 정본에 쓰고 여기서 지운다.
- 한 번 겪으면 적고, 두 번 겪으면 규칙으로 올린다.
- 비슷한 항목이 이미 있으면 새로 쓰지 않고 그 항목의 관련에 이슈를 더한다.

## GitHub 브랜치 보호에 필수 체크가 없으면 PATCH가 404다

- 상황: `branches/<branch>/protection/required_status_checks`를 PATCH했더니 "Required status checks not enabled"로 404가 났다. 브랜치에 필수 체크가 한 번도 켜진 적이 없을 때다.
- 대응: 보호 설정 전체를 PUT으로 올린다. 기존 값(승인 인원, 관리자 적용, force push·삭제 금지)을 먼저 읽어 같은 값으로 함께 보낸다. PUT은 빠뜨린 항목을 끈다.
- 관련: #126

## 테스트 리소스의 application.yaml이 메인 설정을 가린다

- 상황: `src/test/resources/application.yaml`이 메인과 이름이 같아서 테스트에서는 메인 `application.yaml`이 읽히지 않는다. 메인에만 `management.*` 같은 설정을 넣으면 테스트는 그 설정과 무관하게 Spring 기본값으로 통과해서, 설정을 지워도 테스트가 깨지지 않는다.
- 대응: 설정을 검증하는 테스트는 설정이 테스트 yaml에도 있는지 확인하고, 일부러 값을 뒤집었을 때(환경 변수 등) 실패하는지 본다. 두 파일에 같은 설정을 두면 한쪽만 고쳐도 통과하는 한계가 있으니 복제한 이유와 동기화 책임을 주석으로 남긴다.
- 관련: #155

## Flyway 마이그레이션 파일은 주석도 체크섬에 들어간다

- 상황: `V1__init_schema.sql`의 주석에 낡은 문서 참조(`ERD.md §4·§5`)가 남아 있다. 문서 참조를 정리하려고 이 주석을 고치면 파일 내용이 바뀌어, 이미 적용된 DB에서 Flyway 검증이 체크섬 불일치로 실패한다.
- 대응: 이미 적용된 마이그레이션 파일은 주석 한 글자도 고치지 않는다. 낡은 참조는 그대로 두고 새 마이그레이션이나 문서 쪽에서 바로잡는다.
- 관련: #137

## sketch의 구조 칸에 테스트 이름만 적으면 test-writer가 계층을 잘못 고른다

- 상황: sketch 구조 칸에 `PollDeleteWebApiTest`라고만 적었더니 test-writer가 이름은 `…WebApiTest`(슬라이스)인데 실제 DB를 쓰는 체인 방식 테스트 11개를 썼다. `테스트-전략.md`는 controller 슬라이스가 매핑·인자·응답 모양만 보고 오류 매핑·입력 검증은 보지 않으며 체인은 대표 시나리오만 두라고 하는데, 이미 서비스 테스트가 확인한 규칙까지 API에서 반복했다. 이 레포에서 `…WebApiTest`는 슬라이스, `…ChainTest`는 체인이다.
- 대응: sketch의 순서와 테스트 칸에 테스트마다 계층(도메인·서비스 통합·슬라이스·체인)과 무엇을 보는지를 적는다. 사람은 test-writer의 note에서 계층과 개수를 보고 `테스트-전략.md`의 표와 맞는지 확인한다.
- 관련: #76


## 이슈 본문의 호출 지점 수는 그대로 믿지 말고 grep으로 다시 센다

- 상황: #160 본문은 `getActiveMember`를 "5곳"에서 검증으로만 쓴다고 했지만, 실제는 3개 파일 4곳이었다. 센 수로 sketch의 영향 범위와 안전장치를 짜면 범위가 틀어진다.
- 대응: 이름 변경·분리 이슈는 sketch를 쓸 때 `grep`으로 호출 지점을 직접 세어 sketch에 적고, 끝난 뒤 src에 0건인지 확인한다. 이슈 본문과 다르면 sketch에 달라진 점으로 남긴다.
- 관련: #160
