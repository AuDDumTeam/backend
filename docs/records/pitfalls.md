# 교훈

일하다 겪은 함정과 대응을 짧게 남기는 곳이다. 정본이 아니다.

- 항목은 **제목 / 상황 / 대응 / 관련(ID·이슈)** 네 줄로 쓴다.
- 정본(기능 페이지·도메인 모델·컨벤션)이 주인이다. 규칙으로 정할 만하면 정본에 쓰고 여기서 지운다.
- 한 번 겪으면 적고, 두 번 겪으면 규칙으로 올린다.
- 비슷한 항목이 이미 있으면 새로 쓰지 않고 그 항목의 관련에 이슈를 더한다.

## GitHub 브랜치 보호에 필수 체크가 없으면 PATCH가 404다

- 상황: `branches/<branch>/protection/required_status_checks`를 PATCH했더니 "Required status checks not enabled"로 404가 났다. 브랜치에 필수 체크가 한 번도 켜진 적이 없을 때다.
- 대응: 보호 설정 전체를 PUT으로 올린다. 기존 값(승인 인원, 관리자 적용, force push·삭제 금지)을 먼저 읽어 같은 값으로 함께 보낸다. PUT은 빠뜨린 항목을 끈다.
- 관련: #126

## 테스트 리소스의 application.yaml이 메인 설정을 가린다

- 상황: `src/test/resources/application.yaml`이 메인과 이름이 같아서 테스트에서는 메인 `application.yaml`이 읽히지 않는다. 메인에만 `management.*` 같은 설정을 넣으면 테스트는 그 설정과 무관하게 Spring 기본값으로 통과해서, 설정을 지워도 테스트가 깨지지 않는다.
- 대응: 설정을 검증하는 테스트는 설정이 테스트 yaml에도 있는지 확인하고, 일부러 값을 뒤집었을 때(환경 변수 등) 실패하는지 본다. 두 파일에 같은 설정을 두면 한쪽만 고쳐도 통과하는 한계가 있으니 복제한 이유와 동기화 책임을 주석으로 남긴다.
- 관련: #155

## Flyway 마이그레이션 파일은 주석도 체크섬에 들어간다

- 상황: `V1__init_schema.sql`의 주석에 낡은 문서 참조(`ERD.md §4·§5`)가 남아 있다. 문서 참조를 정리하려고 이 주석을 고치면 파일 내용이 바뀌어, 이미 적용된 DB에서 Flyway 검증이 체크섬 불일치로 실패한다.
- 대응: 이미 적용된 마이그레이션 파일은 주석 한 글자도 고치지 않는다. 낡은 참조는 그대로 두고 새 마이그레이션이나 문서 쪽에서 바로잡는다.
- 관련: #137

## sketch의 구조 칸에 테스트 이름만 적으면 test-writer가 계층을 잘못 고른다

- 상황: sketch 구조 칸에 `PollDeleteWebApiTest`라고만 적었더니 test-writer가 이름은 `…WebApiTest`(슬라이스)인데 실제 DB를 쓰는 체인 방식 테스트 11개를 썼다. `테스트-전략.md`는 controller 슬라이스가 매핑·인자·응답 모양만 보고 오류 매핑·입력 검증은 보지 않으며 체인은 대표 시나리오만 두라고 하는데, 이미 서비스 테스트가 확인한 규칙까지 API에서 반복했다. 이 레포에서 `…WebApiTest`는 슬라이스, `…ChainTest`는 체인이다.
- 대응: sketch의 순서와 테스트 칸에 테스트마다 계층(도메인·서비스 통합·슬라이스·체인)과 무엇을 보는지를 적는다. 사람은 test-writer의 note에서 계층과 개수를 보고 `테스트-전략.md`의 표와 맞는지 확인한다.
- 관련: #76

## 이슈 본문의 호출 지점 수는 그대로 믿지 말고 grep으로 다시 센다

- 상황: #160 본문은 `getActiveMember`를 "5곳"에서 검증으로만 쓴다고 했지만, 실제는 3개 파일 4곳이었다. 센 수로 sketch의 영향 범위와 안전장치를 짜면 범위가 틀어진다.
- 대응: 이름 변경·분리 이슈는 sketch를 쓸 때 `grep`으로 호출 지점을 직접 세어 sketch에 적고, 끝난 뒤 src에 0건인지 확인한다. 이슈 본문과 다르면 sketch에 달라진 점으로 남긴다.
- 관련: #160

## test-writer가 이름이 같은 기존 테스트 파일을 읽지 않고 덮어쓴다

- 상황: 기존 `PollListWebApiTest`(케이스 6개)가 있는데 test-writer가 읽지 않고 Write로 새 파일을 만들어 원본이 사라졌다. Write 결과가 "created"가 아니라 "updated"였고, test-writer는 git을 쓸 수 없어 복구하지 못했다. 메인이 `git show HEAD:<경로>`로 원본을 꺼내 합쳤다.
- 대응: test-writer를 부를 때 "sketch가 말한 테스트 클래스가 이미 있으면 먼저 읽고 케이스를 더하는 방식으로 쓴다"를 입력에 적는다. 끝나면 `git status`에서 `M`(수정)인 테스트 파일의 `git diff`에 지워진 줄이 시그니처 변경 밖에 없는지 본다.
- 관련: #162

## 리뷰 diff를 `develop` 기준으로 만들면 분기 뒤 다른 커밋이 섞일 수 있다

- 상황: 리뷰용 diff를 `git diff develop...HEAD`로 만들었더니 이 이슈와 무관한 하네스 문서 변경(#166)이 섞여, 두 리뷰어가 범위 이탈을 지적했다. 로컬 `develop`이 브랜치에 들어온 커밋보다 뒤처져 있었다.
- 대응: 구현이 시작되기 전 마지막 커밋(sketch 승인 커밋)을 기준으로 `git diff <sketch 커밋>..HEAD`를 만든다. 리포트에 이슈와 무관한 파일이 보이면 diff 기준부터 의심한다.
- 관련: #162

## sketch 질문에 선택지의 구현 비용을 적지 않으면 우회가 승인 뒤에 드러난다

- 상황: "모르는 `category` 값은 전체로 본다"를 사용자가 골랐는데, 그 선택이 열거형 바인딩을 못 쓰고 문자열로 받아 직접 해석하는 우회(`PollListRequest.categoryFilter()`, `ALL`, 해석 단위 테스트)를 강제한다는 점이 질문에 없었다. 구현과 PR까지 끝난 뒤 사용자가 "열거형으로 받으면 안 되느냐"고 물어서 sketch를 되돌리고 구현을 다시 고쳤다.
- 대응: 규칙을 고르는 질문에는 각 선택지가 구현에 강제하는 것(타입, 해석 코드, 추가 테스트, 정본 문장)을 한 줄씩 함께 적는다. 특히 프레임워크 기본 동작(열거형 변환, 400 매핑)을 거스르는 선택지는 "기본 동작을 쓰는 안"과 나란히 보인다.
- 관련: #162, #179

## 이름 기준 grep으로 "패키지 밖에서 안 쓰는 public"을 찾으면 체이닝 사용을 놓친다

- 상황: 접근 제한자를 좁히려고 클래스 이름이 다른 패키지 파일에 나오는지로 후보를 뽑았더니 `poll` 도메인 값 객체 5개(`PublicId`, `PollQuestion` 등)가 후보에 올랐다. 다른 패키지는 `poll.getQuestion().value()`처럼 타입 이름을 쓰지 않고 체이닝으로 부르기 때문에 이름 grep에는 안 걸렸다. 좁히고 컴파일하자 `value() is defined in an inaccessible class`로 14곳이 깨졌다.
- 대응: 접근 제한자는 grep으로 후보만 뽑고, 실제로 좁힌 뒤 `compileJava compileTestJava`로 판정한다. 깨지는 것은 되돌리고 이유를 sketch 결과에 적는다. 테스트가 다른 패키지에서 직접 쓰는 것도 같은 방식으로 드러난다.
- 관련: #174

## test-writer는 grep을 못 써서 목록 밖의 기존 테스트 기대값을 놓친다

- 상황: 동작이 바뀌는 이슈(없는 회원 401→404)에서 sketch가 적은 테스트만 고쳤다. test-writer의 Bash는 `gradlew`만 허용해서 `grep`을 못 쓰고, 목록 밖의 "없는 회원 401"을 기대하는 테스트 둘(`ReportSubmitChainTest`, `VoteCommandServiceTest`)은 구현 뒤 전체 `./gradlew test`에서야 실패로 드러났다.
- 대응: 동작이 바뀌는 이슈는 test-writer를 부르기 전에 메인이 `grep`으로 바뀌는 기대값을 가진 테스트 파일을 전부 찾아 입력에 파일 목록으로 준다. 구현 뒤 전체 `./gradlew test`는 목록 밖의 빈틈을 잡는 안전망이다.
- 관련: #174

## sketch 질문의 선택지가 이미 정한 설계 결정을 뒤집을 수 있다

- 상황: "`Voter`는 `AnonId`, `Reporter`는 `UUID`인 차이를 어떻게 맞출까"를 선택지 A(`AnonId`를 옮겨 공유)·B(`UUID` 통일)·C(유지)로 올렸는데, `설계-결정.md`가 이미 "`Vote`와 `Report`는 값 객체를 공유하지 않는다"고 정해 두었다. A·B는 그 결정을 뒤집는 안이었다. sketch-reviewer가 지적하기 전까지 질문에 이 사실이 없었다.
- 대응: 질문을 올리기 전에 `설계-결정.md`에서 관련 항목을 찾아, 이미 정한 결정이 있으면 질문에 그 사실과 근거를 먼저 적는다. 선택지가 결정을 뒤집으면 "정본 수정 필요"라고 표시한다.
- 관련: #174

## 기존 호출이나 리뷰어 제안을 같은 일을 하는 클래스가 있는지 확인하지 않고 쓰면 계층이 어긋난다

- 상황: 읽기 API가 회원 상태만 확인하면 되는데, `MemberReader.getNotWithdrawnMember`(회원을 돌려주는 `get`)를 불러 반환값을 버렸다. sketch-reviewer가 이 이름을 권해서 그대로 받았다. 검증은 `MemberValidator`가 맡는 구조(#160)가 이미 있었다. 같은 PR에서 요청 DTO(`PollListRequest`)로 쿼리 파라미터를 묶었다가 `cursorId()`, `pageSize()`로 풀어 넘겨 "서비스 인자는 개념별 record로 묶는다"(`설계-결정.md`)도 어겼다. 테스트는 통과해서 둘 다 사용자가 짚을 때까지 남았다. sketch-reviewer는 정본 충돌만 보고, 이름·계층 배치는 보지 않는다.
- 대응: 새 메서드를 쓰기 전에 같은 일을 하는 기존 클래스(`*Validator`, `Viewer`·`PollChoice` 같은 묶음 record)가 있는지 `설계-결정.md`와 이웃 클래스에서 먼저 찾는다. 반환값을 버리는 호출은 이름이 틀렸다는 신호로 본다. 리뷰어가 권한 이름도 컨벤션과 맞는지 직접 확인한다.
- 관련: #163, #179

## 빌드 통과 뒤 커밋 전에 파일이 바뀌어도 모르면 결함이 커밋에 들어간다

- 상황: `./gradlew build`가 통과한 뒤 커밋하기 전에 `MyPollListResponse.of`가 `getLast()`를 `hasNext()` 확인 앞에서 부르는 모양으로 바뀌어 있었다(원인 미확인, 편집기 등 다른 곳의 수정으로 보인다). 그대로 커밋했고 리뷰어 둘이 "올린 투표가 없으면 500"으로 잡았다.
- 대응: 커밋 직전에 `git diff`로 의도한 변경인지 확인하고 `./gradlew build`를 다시 돌린다. 빈 목록 같은 경계 테스트가 있으면 그것이 방어선이다.
- 관련: #163

## 문서만 바꾼 뒤 `./gradlew build`는 캐시된 테스트로 통과해서 생성 문서 불일치를 놓친다

- 상황: 정본(기능 페이지의 "사용하는 API" 표)을 고친 뒤 `./gradlew build`가 1초 만에 `BUILD SUCCESSFUL`이었다. `API-목록.md`의 "기능" 칸은 기능 페이지의 API 표에서 만들어지는데, `docs/`는 Gradle 테스트 작업의 입력이 아니라서 테스트가 `UP-TO-DATE`로 건너뛰어졌다. 그대로 PR을 올렸더니 CI에서 `OpenApiDocTest > API_목록이_코드와_같다()`가 실패했다.
- 대응: 정본이나 기능 페이지의 API 표를 고친 뒤에는 `./gradlew cleanTest build`로 테스트를 다시 돌리고, 필요하면 `DOCS_UPDATE=1 ./gradlew test --tests '*OpenApiDocTest'`로 생성 문서를 다시 만든다. wrap에서 정본을 고친 뒤에는 `UP-TO-DATE`가 아닌 실행을 확인한다.
- 관련: #163


## 포트가 id 쌍만 돌려주도록 정하면 서비스가 다시 읽고 짜 맞추게 된다

- 상황: 참여 목록 포트를 (`vote.id`, 투표 id) 쌍으로 정해 sketch가 승인되었다. 구현하니 서비스가 투표를 `findAllByIds`로 다시 읽고 `Map`으로 짜 맞추는 코드가 몰려 사용자가 두 번 복잡하다고 지적했다. 리뷰어들은 승인된 계약을 전제로 보아 이 구조 자체를 문제 삼지 않았다. 호출자가 결국 필요한 것(`Poll`)을 포트가 돌려주고, join이 허용되는 방향(`vote → poll`)인데도 sketch에서 비교하지 않았다.
- 대응: 포트나 repository의 반환 모양을 정할 때 "호출자가 받은 뒤 다시 읽거나 조립해야 하는가"를 sketch의 선택지로 올리고, 서비스가 몇 줄이 될지 비교한다. 구현이 sketch 접근보다 복잡해 보이면 리뷰에 맡기지 말고 접근을 다시 묻는다.
- 관련: #163

## API 설명문은 응답 필드를 바꿔도 따라 바뀌지 않는다

- 상황: 참여 목록 항목에서 참여 수를 뺐는데 `@Operation(description)`과 생성된 `openapi.json`에 "참여 수를 담는다"가 남았다. 응답 스키마와 테스트는 맞았고 도메인 리뷰어가 잡았다.
- 대응: 응답 필드를 더하거나 빼면 해당 `*WebApiDocs`의 설명문도 같이 고치고 `DOCS_UPDATE=1`로 생성 문서를 다시 만든다. 스키마는 자동이지만 문장은 손으로 쓴 것이다.
- 관련: #163
