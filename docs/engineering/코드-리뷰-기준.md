# 코드 리뷰 기준

관련 문서: [설계-결정](설계-결정.md), [컨벤션](컨벤션.md), [아키텍처](아키텍처.md), [인증](인증.md), [테스트 전략](테스트-전략.md), [개발 워크플로](../howto/개발-워크플로.md)

## 요약

코드를 리뷰할 때 **무엇을 어떻게 볼지** 정한다. 사람과 AI 리뷰어가 같은 기준을 쓴다.

- 리뷰는 둘로 나눈다. 정책·문서와 맞는지(도메인 리뷰)와 설계·품질(코드 리뷰)이다. 같은 위치에는 지적을 하나만 쓴다.
- 코드 리뷰는 의존, 책임·역할, 협력, OOP, DDD를 중심으로 본다.
- 이 프로젝트가 정한 설계 규칙을 어기면 차단이다. 규칙 문장은 근거 문서가 기준이고 여기에는 옮겨 적지 않는다.
- 코드 컨벤션과 보안은 설계와 함께 매번 본다. 컨벤션의 규칙 목록은 [컨벤션](컨벤션.md)이 기준이라 여기에 옮기지 않는다.
- [설계-결정](설계-결정.md)에 적힌 결정과 알려진 한계는 다시 지적하지 않는다.
- 판정은 `PASS`, `PASS_WITH_FIXES`, `FAIL`이다. 차단이 하나라도 있으면 `FAIL`이다.

## 1. 도메인 리뷰

변경이 문서의 정책·도메인 모델·API 문서와 맞는지만 본다. 코드 결함(NPE, N+1 등)은 보지 않는다. 아래 ID에 없는 위반은 지적하지 않고 질문으로 남긴다.

차단 기준:

| ID | 기준 | 근거 문서 |
|---|---|---|
| 정책-차단-1 | 문서의 정책·규칙에 대응하는 구현이나 테스트가 없다 | 기능 페이지의 정책 정의·규칙 표, 도메인 모델 |
| 정책-차단-2 | 경로·메서드·상태 코드·오류 코드가 생성된 API 문서와 다르다 | `generated/` 문서 |
| 정책-차단-3 | 도메인 규칙(마감, 상태 전이, 선택지 소속)이 서비스나 controller에 있다 | 도메인 모델, 아키텍처 |
| 정책-차단-4 | 상태 전이·enum 값·용어가 도메인 모델과 다르다 | 용어집, 도메인 모델 |
| 정책-차단-5 | 기능 페이지에 없는 엔드포인트·필드·정책을 추가했다 | 기능 페이지의 사용하는 API, 정책 정의 |
| 정책-차단-6 | 동작이 바뀌었는데 관련 문서가 그대로다 | 개발 워크플로 |

권고 기준:

| ID | 기준 |
|---|---|
| 권고-1 | 예외 경로 테스트가 정상 경로보다 부족하다 |
| 권고-2 | 테스트 이름·구성이 [컨벤션](컨벤션.md)·[테스트 전략](테스트-전략.md)과 다르다 |
| 권고-3 | 코드 이름이 용어집과 다르다(투표=Poll, 참여=Vote) |

### 누구 몫인가

구현이 문서와 다르면 구현자, 테스트가 없거나 기대값이 문서와 다르면 테스트 작성자, 문서가 낡았거나 모호하면 문서(사용자 확인이 필요하다)다.

## 2. 코드 리뷰

### 우선순위

가장 중요한 것은 유지보수와 장애 대응에 쉬운 코드, 그리고 누가 봐도 알기 쉬운 코드·포맷·네이밍이다. 지적이 많으면 이 순서로 남긴다.

1. 장애 대응성: 장애가 났을 때 원인을 빨리 찾을 수 있는가
2. 가독성·네이밍·포맷: 처음 보는 사람이 읽고 이해하는가
3. 유지보수성: 한 곳을 바꿀 때 고칠 곳이 몇 군데인가
4. 그 밖의 영역(성능·JPA, 보안, 마이그레이션 등)

### 판정 ID

차단 기준:

| ID | 기준 | 비고 |
|---|---|---|
| 코드-차단-1 | [아키텍처](아키텍처.md), [설계-결정](설계-결정.md), [컨벤션](컨벤션.md)에 적힌 규칙을 어겼다 | 어긴 규칙과 근거 문서를 적는다 |
| 코드-차단-2 | 입력·상태에서 장애로 이어지는 구체적인 실패 시나리오를 댈 수 있다 | 시나리오를 적는다 |
| 코드-차단-3 | 구체적인 공격 시나리오를 댈 수 있는 보안 취약점(OWASP Top 10 범주) | 시나리오를 적는다 |

권고 기준:

| ID | 영역 | 기준 |
|---|---|---|
| 코드-권고-1 | 책임 분배 | 로직이 맞는 계층·애그리거트에 있지 않다 |
| 코드-권고-2 | DDD·OOP | 불변식, 값 객체, 다형성, 빈약한 모델, 결합도 |
| 코드-권고-3 | 일관성 | 주변 코드 3곳 이상과 다르다 |
| 코드-권고-4 | 가독성·네이밍·포맷 | 길이, 중첩, 이름, 중복, 주석, 쓰이지 않는 코드, 과한 추상화, 주변 코드와 다른 포맷 |
| 코드-권고-5 | 성능·JPA | N+1, 불필요한 조회, 인덱스, 지연 로딩, 영속성 컨텍스트, 페이징 |
| 코드-권고-6 | 장애·안정성·대응성 | 시나리오를 대기는 어렵지만 트랜잭션·동시성·멱등성·예외 처리가 우려된다. 로그·예외 메시지로 원인을 찾기 어렵다 |
| 코드-권고-7 | 보안 | 공격 시나리오는 약하지만 OWASP 범주상 보강이 필요하다 |
| 코드-권고-8 | 마이그레이션·API 계약 | 마이그레이션 안전성, 하위 호환, 멱등성 |
| 코드-권고-9 | 테스트 품질 | 취약한 테스트, 경계·실패 경로 부족, 픽스처 중복 |

컨벤션에 적힌 규칙은 취향이 아니라 약속이라 차단이다. 문서에 없는 취향 차이는 권고도 아니고 쓰지 않는다. 테스트 이름·구성은 도메인 리뷰의 권고-2가 맡고, 코드 리뷰는 테스트 품질(코드-권고-9)만 본다.

## 3. 설계 점검표

원칙으로 읽는다. 같은 원칙을 어긴 곳은 어디든 지적한다. 반대로 겉모양만 닮고 이유가 해당하지 않으면 지적하지 않는다. 규칙의 문장과 예외는 근거 문서에 있다. 구조 검사 도구가 잡는 것은 빌드가 먼저 실패하므로, 리뷰에서는 우회한 흔적만 본다.

### 의존

| 원칙 | 이유 | 근거 |
|---|---|---|
| 의존은 한 방향으로 흐르고, 가장 안쪽인 도메인은 바깥 레이어를 모른다 | 바깥(웹, 저장소)을 바꿔도 핵심 규칙이 흔들리지 않는다 | [아키텍처](아키텍처.md) |
| 레이어를 건너뛰지 않는다. 서비스는 데이터 접근을 직접 하지 않고 구현 계층에 맡긴다 | 한 레이어가 한 수준의 일만 하게 한다 | [아키텍처](아키텍처.md) |
| 다른 도메인과는 그 도메인이 열어 둔 진입점으로만 협력한다. 내부(저장소, 서비스)를 직접 쓰지 않는다. 조합하는 계층도 예외가 아니다 | 상대의 내부를 바꿔도 이쪽이 깨지지 않는다 | [아키텍처](아키텍처.md) |
| 도메인 사이 의존에 순환이 없다. 생기면 방향을 뒤집는 장치(포트, 이벤트)로 푼다 | 순환은 한쪽만 따로 이해하고 바꿀 수 없게 만든다 | [아키텍처](아키텍처.md) |
| 여러 도메인의 값을 붙여 보여줄 때는 그 화면의 주인 도메인이 조회를 맡는다 | 화면의 필드가 바뀌어도 조회의 위치는 바뀌지 않는다 | [아키텍처](아키텍처.md) |
| 기술 기반 코드는 도메인을 모른다. 주인 없는 공용 패키지를 만들지 않는다 | 규칙이 주인 없이 쌓여 아무도 책임지지 않게 되는 것을 막는다 | [아키텍처](아키텍처.md) |

### 책임과 역할

| 원칙 | 이유 | 근거 |
|---|---|---|
| 서비스는 처리 순서와 트랜잭션만 맡는다. 세부 로직은 구현 계층이, 규칙은 도메인 객체가 맡는다 | 규칙이 바뀔 때 고칠 곳이 한 곳이다 | [아키텍처](아키텍처.md) |
| 한 클래스는 한 가지 일을 하고 이름이 그 일을 말한다 | 이름만 보고 필요한 코드를 찾을 수 있다 | [아키텍처](아키텍처.md) |
| 경계(트랜잭션)를 정하는 일은 서비스가 한다. 구현 계층은 부른 쪽의 경계에 참여한다 | 경계가 여러 곳에서 정해지면 어디까지 한 덩어리인지 알 수 없다 | [설계-결정](설계-결정.md) |
| 서비스는 도메인 객체를 돌려주고 응답의 모양은 표현 계층이 정한다. 객체 하나로 표현되지 않는 목록·집계·조합만 조회 전용 객체를 쓴다 | 표현 관심사가 안쪽으로 들어오지 않게 한다 | [아키텍처](아키텍처.md) |
| 정책 판단을 표현 계층으로 올리지 않는다. 표현 계층은 결과를 변환만 한다 | 같은 규칙이 진입점마다 다르게 구현되는 것을 막는다 | [아키텍처](아키텍처.md) |
| 같은 역할은 같은 방식으로 표시한다 | 선언만 보고 역할을 알고, 구조 검사가 역할 기준으로 돈다 | [아키텍처](아키텍처.md) |

### 협력

| 원칙 | 이유 | 근거 |
|---|---|---|
| 판단은 그 정보를 가진 쪽이 하고, 상대는 사실만 돌려준다 | 판단 기준이 한 곳에만 있어야 어긋나지 않는다 | [설계-결정](설계-결정.md) |
| 다른 객체의 정보가 필요한 판단은 서비스가 정보를 모으고, 규칙은 도메인 객체에 둔다. 비싼 조회는 필요할 때만 한다(지연 평가) | 규칙의 위치를 지키면서 불필요한 조회를 피한다 | [설계-결정](설계-결정.md) |
| 협력의 계약은 필요한 만큼만 좁게 연다 | 계약이 넓으면 상대의 변경이 이쪽까지 번진다 | [설계-결정](설계-결정.md) |
| 쓰기를 처리하는 서비스는 요청한 사람의 자격(회원 상태)을 첫 단계에서 확인한다 | 자격이 바뀌는 일이 로그인 중에도 일어난다 | [인증](인증.md) |

### OOP

| 원칙 | 이유 | 근거 |
|---|---|---|
| 값을 꺼내 밖에서 판단하지 말고 객체에게 시킨다(Tell, Don't Ask) | 판단이 객체 밖으로 새면 같은 판단이 여러 곳에 생긴다 | [아키텍처](아키텍처.md) |
| 불변식은 객체가 지킨다. 상태를 바꾸는 길은 의도를 드러내는 메서드뿐이고 setter를 열지 않는다 | 잘못된 상태의 객체가 만들어질 길을 막는다 | [아키텍처](아키텍처.md), [컨벤션](컨벤션.md) |
| 공개 범위는 가장 좁게 둔다. 밖에 여는 것은 약속한 진입점뿐이다 | 열린 만큼 바꾸기 어려워진다 | [아키텍처](아키텍처.md) |
| 모양이 같다는 이유만으로 합치지 않는다. 뜻과 바뀌는 이유가 같을 때만 합친다 | 같은 모양이라도 다르게 쓰일 수 있고, 같은 뜻이라도 다른 말일 수 있다 | [설계-결정](설계-결정.md) |

### DDD

| 원칙 | 이유 | 근거 |
|---|---|---|
| 애그리거트 사이는 객체가 아니라 ID로 참조한다 | 한 트랜잭션에서 바꾸는 범위와 일관성 경계를 분명히 한다 | [아키텍처](아키텍처.md) |
| 값 객체는 애그리거트 사이에 공유하지 않는다 | 애그리거트마다 같은 말이 다른 규칙을 가질 수 있고, 한쪽의 변경이 다른 쪽으로 번지지 않아야 한다 | [설계-결정](설계-결정.md) |
| 도메인 서비스는 한 객체가 갖기 어려운 규칙만 두고 상태를 갖지 않는다 | 서비스에 규칙이 쌓이면 객체가 빈약해진다 | [아키텍처](아키텍처.md) |
| 도메인 이벤트는 결합이나 순환을 풀어야 할 때만 쓰고, 늘릴 때는 결정 문서를 먼저 고친다 | 이벤트가 늘면 흐름을 따라가기 어렵다 | [설계-결정](설계-결정.md) |
| 코드의 이름은 용어집의 말과 같다. 같은 말은 같은 뜻으로, 다른 뜻은 다른 이름으로 쓴다 | 문서·대화·코드가 같은 말을 해야 오해가 없다 | [용어집](../domain/용어집.md) |

## 4. 항상 같이 보는 것

설계 점검표와 함께 매번 본다. 변경이 건드리지 않은 부분은 보지 않는다.

### 컨벤션

[컨벤션](컨벤션.md)을 읽고 변경한 코드를 대조한다. 거기에 적힌 규칙을 어기면 차단이다(코드-차단-1). 규칙의 목록은 컨벤션이 기준이라 여기에 옮기지 않는다. 문서에 없는 취향 차이는 쓰지 않는다.

### 보안

OWASP Top 10 범주 중 변경에 걸리는 것을 본다. 번호는 판마다 달라 범주 이름으로 적고, 구체적인 공격 시나리오를 댈 수 있으면 차단(코드-차단-3), 아니면 권고(코드-권고-7)다.

- 접근 통제: 소유자·관리자·회원 상태 확인 누락, ID를 추측해 남의 자원에 접근, 404와 403 선택으로 존재 여부가 드러나는지
- 인증: 토큰·익명 쿠키의 서명 검증, 리프레시 토큰 재사용과 탈취 대응
- 인젝션: 검증하지 않은 입력이 쿼리·경로·헤더로 들어가는 곳
- 민감 정보: 로그·응답·예외 메시지에 토큰, 쿠키 원문, 개인정보가 남는지
- 설정과 우회: CORS·쿠키 속성(HttpOnly, Secure, SameSite), 반복 시도 제한 부재, 비즈니스 로직 우회
- 구성요소: 새 의존성의 필요성과 유지 상태

### 장애 대응성

- 실패했을 때 로그와 예외만 보고 원인을 가를 수 있는가. 서로 다른 실패가 같은 오류로 뭉개지거나 원인 예외가 끊기지 않는가.
- 삼켜진 예외, 트랜잭션 경계, 동시 요청, 경계값을 본다.

### 일관성과 가독성

- 주변 코드와 같은 방식인가(이름, 예외, 응답 형태, 의존 방향). 주변 코드 3곳 이상을 비교한 근거가 있어야 지적하고, 취향 차이면 쓰지 않는다.
- 이름이 의도를 드러내는가. 메서드 길이와 중첩, 중복, 쓰이지 않는 코드, 과한 추상화를 본다.
- 주석은 "무엇"이 아니라 "왜"를 설명해야 하고, 코드와 어긋난 주석은 거짓이라 고친다.

## 5. 변경이 있을 때 보는 것

- 성능·JPA(`코드-권고-5`): N+1과 불필요한 조회, 지연 로딩, 페이징·정렬 안정성
- 마이그레이션·API 계약(`코드-권고-8`): 기존 데이터에서의 적용과 롤백, 응답 필드의 하위 호환
- 테스트 품질(`코드-권고-9`): 구현을 그대로 따라 쓴 취약한 테스트, 경계·실패 경로 부족, 픽스처 중복

## 6. 이 프로젝트의 사례

실제 리뷰에서 나온 지적을 모양만 남겨 적었다. 클래스와 메서드 이름은 바뀌므로 적지 않는다. 새 사례가 쌓이면 한 줄씩 더한다.

| 영역 | 지적 | 고친 방향 |
|---|---|---|
| 책임 분배 | 서비스가 공개 여부, 작성자, 관리자 여부를 직접 조합해 열람 규칙을 만들었다 | 규칙을 도메인 객체의 메서드로 옮기고, 조회가 필요한 조건은 필요할 때만 평가하도록 넘긴다 |
| DDD·OOP | 조회 클래스의 람다 안에 상태 판단 조건을 풀어 썼다 | 판단을 도메인 객체의 메서드로 옮겨 조회는 조회 클래스가, 판단은 객체가 맡게 한다 |
| 장애 대응성 | 제약 위반을 도메인 오류로 바꾸면서 원인 예외를 버려, 동시 요청의 실패와 재전송의 실패가 로그에서 같아 보였다 | 원인 예외를 체인으로 잇는다 |
| 가독성 | 클래스 설명이 "다른 도메인에 여는 진입점은 하나뿐"이라고 했는데 다른 도메인이 둘째 진입점도 쓰게 되어 거짓이 됐다 | 코드를 바꿀 때 설명도 같이 고친다 |
| 일관성 | 같은 역할의 협력 객체가 대부분 한 방식으로 표시되는데 하나만 다른 방식이었다 | 같은 방식으로 맞춘다 |
| 테스트 품질 | 도메인 객체에 둔 규칙이 단위 테스트 없이 통합 테스트로만 확인됐다 | 가장 낮은 계층의 테스트가 규칙을 전수로 확인하게 한다 |
| 불필요한 코드 | 쓰는 곳이 없는 조회 메서드가 있었다 | 쓰는 변경에서 만든다 |
| 오탐 주의 | null과의 비교가 true일 수 있다는 지적 | 비교 방식과 컬럼 제약을 열어 보니 안전했다. 코드를 확인한 뒤에 지적한다 |

## 7. 설계 제안

판정과 관계없이 선택으로 낸다. 프로젝트 규모(MVP, 서버 1대, MySQL 단일)에 맞는 것만 낸다. 메시지 브로커, 분산 락, 저장소 분리는 제안하지 않는다.

```markdown
### SP-n: <제목>
- 대안: <무엇을 어떻게 바꾸는가>
- 얻는 것: <지금 코드에서 실제로 보이는 문제를 어떻게 줄이는가>
- 비용: <바꿀 곳, 테스트, 복잡도>
- 도입 시점: <지금 / 어떤 신호가 보일 때>
```

예:

- 도메인 이벤트로 분리한다. 결합은 줄지만 구독자가 하나면 보류한다.
- 비동기 처리로 바꾼다. 응답 지연이 문제가 될 때 낸다.
- 같은 입력 처리가 여러 컨트롤러에 반복되면 웹 계층의 인자 처리 장치로 모은다.
